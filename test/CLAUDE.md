# Tests

`/tdd` has the loop and what a good test is. This file has what spec #1 already decided for this repo, and how the harness works.

## The agreed seams

Spec #1 agreed two seams. Test at these; propose any other seam before writing a test at it.

- **Seam 1: the MCP tools as a black box.** A test starts the fake OLIS at a clock time, runs the ingest worker, and calls tools through an MCP client. It then moves the clock, runs an increment, and calls them again. It asserts what an agent would see.
- **Seam 2: parser tables.** Extracted document text goes in; Statute Links or Agency Links come out. There is one row per wording variant (`test.for`), and each row quotes a real document and names it.

Seam-1 tests read state back through the tools, never through tables, SQL or internal types, so storage and ranking can change without touching a test. Seam-2 tests call a parser package's entry point directly: that entry point is the seam.

## Expected values

Expected values are literals from an independent source:

- the spec's worked examples, such as HB 3131's 42 Testimony rows (41 support, 1 oppose), or SB 69-2, adopted by SLB on 2025-01-30;
- the Statutes Affected Table;
- the document itself.

## The harness

- **Fake OLIS.** An in-process `node:http` server on `127.0.0.1:0` replays `test/fixtures/` as the feed stood at the clock time. It reproduces the real feed's quirks: `$inlinecount`, 5,000-row pages with a relative `odata.nextLink`, `/$count` answered only without a JSON `Accept` header, misspelled property names, and decimal keys as strings. Its `$filter` is a conjunction of `eq` and `ge datetime'...'` terms, as the live lookup sends, and the increments' parenthesised `(CreatedDate gt datetime'...' or ModifiedDate gt datetime'...')` group (`gt` and `or`, ticket #17); anything else is refused. A test changes it after the pull with `behave` (answer, fail with a status, hang, or drop the connection), `amendRows`, `addRows` and `withholdLastRows` (all sets, or the one set named), and reads the requests it received with `requests()`. An entity set the fixture holds no file for (CommitteeMembers, whose personal names the fixture's README keeps out) is served empty, as the real service serves a set with no rows for the Session. To make OLIS stop listing a row, and list it again, a test calls `stopListing` and `listAgain` (`test/support/unlisted-rows.ts`): they move the row to another Session with `amendRows`, so the pull's `$filter` and `$count` leave it out. Because it fakes OLIS at the wire, the OLIS client's quirk handling runs in every seam-1 test, which a mocked OLIS adapter would skip.
  - **Documents.** The feed is always served whole, rows that link documents included. With `documents: true` it also serves the documents themselves, at the paths of the manifest's `source_url`s (`/liz/2025R1/Downloads/...`) on the same port. The worker is pointed at them with `OLIS_DOCUMENT_ORIGIN` (`olis.origin`), so no test reaches the real OLIS: every test that runs the worker sets it, whether or not the files are served (the entry-script test builds the worker's environment in one helper). The files are off by default, because pulling the fixture's 278 documents takes about four seconds and a test of `get_measure` reads none; the fake then answers each document request 404, and the worker lists the document as not fetched.
  - **Counts and failures.** `olis.documentRequests()` lists every document request, so a test reads how often a file was fetched from the harness and never from the database. `documentFailures` makes a chosen document hang past the worker's timeout, or answer a status, before it is served; `strayRows` and `strayDocuments` add a row the fixture lacks, with a fixture file served for it.
  - **The Statutes Affected Table.** It is not a feed document (no row links it, and it is on www.oregonlegislature.gov), but the fixture's manifest holds it at `/AutoPubs/artables2025R1.pdf` and the fake serves that path like a document, with `documents: true`. `startSystem`'s `statutesAffectedTableUrl` option (`tableUrlOn`, `test/support/statutes-affected-table.ts`) sets the worker's `STATUTES_AFFECTED_TABLE_URL` to it; unset, the worker never asks. A test serves another table from then on with `olis.serveDocument(path, bytes)`, a made-up one built by `madeUpTable` (`made-up-pdf.ts` writes a PDF from lines of text) and labelled so, and withdraws it with `olis.failDocuments(sourceUrl, [404])`. The seam-2 rows are `statute-links/tests/table-entries.test.ts` (passages of the PDF.js text) and `table-fixture.test.ts` (the whole table); the seam-1 files are `get-measure-statutes-affected-table.test.ts` (one database of the whole fixture, the table loaded) and `get-measure-statutes-affected-table-pull.test.ts` (a system for each story of the table: not published yet, failing, withdrawn, changed, unread, refused, and made-up tables in shapes 2025R1 never shows: an unreadable row, a footer date in November, overturned vetoes, an E alone for a Measure with and without an E-Engrossed Version in the feed; the 2025R1 feed lists none, so that Version is a made-up row added with `addRows`, its file served or not). `madeUpTablePages` writes a made-up table of several pages with the footer date glued to each page's last row, as PDF.js writes the real one.
- **Clock.** One injected `Clock` drives the fake OLIS, the worker and the server. Global fake timers freeze `performance` for the whole worker, so seam-1 tests move the injected clock instead.
- **Time zone.** The Vitest config sets `TZ` to a zone other than Pacific before workers start. Code that quietly relies on local time then fails.
- **Database.** A WAL file in a disposable temp directory, because WAL can't run in memory.
  - Read-only acceptance cases share one database per file: a copy of the run's template for their options (see Templates), or one built by the file where the pull or the embedder is the subject.
  - Cases that change state (increments, removals, revised agendas) build their own.
  - Keep the two kinds in separate files.
  - **Templates (ticket #47).** A system the suite needs more than once is built once per test run and copied. `startCopiedSystem(options)` and `systemTemplate(options).start()` (`test/support/system.ts`) run the full pull for those options the first time any file asks, checkpoint the WAL into the database file, and keep the files in the run's template folder (`test/support/template-cache.ts`, Vitest's global setup: a new folder for each run, removed at its end). Every case gets a fresh fake OLIS at the same clock and a full copy of the files in a temp directory of its own, so no case can change another's data. The key is a hash of what decides the pull (clock, Session, documents, the fake's rows, the snapshot's bytes, the table's address, the alias file), so two files with the same inputs share one build. A test that passes its own `embedder` is not copied, and neither is a system with the Statutes Affected Table (its address is the fake's origin, which a copy does not share): each file builds those once, as before. A copy's fake OLIS has received no request, so a case that reads `olis.documentRequests()` or `requests()` for the first pull's traffic, or that reads the origin stored in the database (the Statutes Affected Table's `source_url`), pulls for itself.
  - **Which cases copy.** Cases that only read, and cases that change the fake or the clock and then pull again, so that the second pull is the subject and fetches and embeds only what the change adds: `find-measures-pull` (made-up rows read as they stand, the Department case with its made-up snapshot, and the first pull of the cases that move the clock), `agency-links-snapshot` and `statute-links-snapshot` (the first pull, of the committed snapshot; the pull after `changeIt()` is real), the cases of `get-measure-statute-links-pull` and `testimony-made-up` that only read or move a row, and every shared read-only file (`get-measure`, `get-document`, `agency-links`, `compare-amendment`, `find-measures`, `find-measures-since`, `search-whole-session`, `search-agency`, `testimony`, `testimony-letters`, `testimony-large`, `meetings-past`, `get-measure-statute-links`, `-sponsors`, `-votes`, `-location`, `-analysis`, `-rate-limit`, `-http`).
  - **Which cases pull.** Those whose subject is the pull: increments (the second pull of a case that moves the clock), refused pulls, fetch counts and failures (`get-document-pull`, `get-measure-analysis-pull`, `compare-amendment-pull`, the `-feed` files, `full-pull-report`, `committee-members`), the two-pull rule (`no-longer-listed*`), the Statutes Affected Table's stories (`get-measure-statutes-affected-table*`, `statutes-affected-table-snapshot`, `get-measure-same-links-as-table-pull`), the search index's reuse of passages (`search-index`), and the files whose every case is built from rows of its own (nothing to share). `search.test.ts` and `search-keyword-only.test.ts` embed with the real model and pull for themselves.
  - A database built before the listing tables is made by `forgetListing` (`test/support/old-database.ts`) after the first pull: it empties `feed_row` and `feed_pull`, which is the state the upgrading worker leaves (it creates the tables empty). It is SQL, used only to arrange; every assertion goes through the tools.
- **MCP client.** Drive `createMcpHandler` in-process through `handler.fetch`, once with a 2026-07-28 client and once with a legacy client. Call `listTools()` first so the client validates `structuredContent`. One test runs on a real port for the Node adapter, the `Host` and `Origin` guards, and the mount path.
- **One system.** `startSystem` (`test/support/system.ts`) starts the fake OLIS at a simulated time, runs the ingest worker's full pull into a temp database and builds the MCP handler, wiring the packages through their entry points the way `src/bin/` does. It refuses to run under the Pacific zone, so a lost `TZ` setting fails loudly. Its `documents` option turns the documents on (default off), `documentTimeoutMs` shortens the worker's wait for a hung document, and the worker never pauses between attempts. `buildReport()` reads the `build-report.json` the worker wrote beside the database. Its `legislatorAliasesPath` option gives the worker an alias file of its own (`test/support/alias-file.ts` writes one), where the entry script passes the committed one. Its `ingest` option sets `INGEST_INCREMENTS` and `INGEST_FULL_PULL` for the worker and the server. Its `incrementAgain()` runs an increment at the clock's time now, and `runSchedule(until)` runs the worker's loop until the simulated clock reaches `until`, its sleep moving that clock (no timer runs; ticket #17). Its `pullAgain()` runs the full pull again after a test moves the clock or changes the fake (for example `olis.withholdLastRows(1)`, so the pull is refused and the test reads the tools to see the index stayed as it was, and `build-report.json` to see which sets were short). `hashSampleReport()` reads the `hash-sample-report.json` of the nightly hash sample (ticket #20); `everyRequestTakes(ms)` makes each request to the fake OLIS move the simulated clock on, so a run is seen to cross a moment; `ingest.hashSampleSize` sets INGEST_HASH_SAMPLE_SIZE and `random` is the randomness the sample draws with (`() => 0`, the first documents by id, unless a test gives another).
- **The snapshot.** `startSystem` gives the worker the committed snapshot fixture (`test/fixtures/oregonai-snapshot/`, ticket #10) as `SNAPSHOT_PATH`; its `snapshot` option gives another path. A test that needs a snapshot with a version of its own writes a made-up one (`test/support/made-up-snapshot.ts`) and says so; a test that pulls twice and changes the snapshot between the pulls takes `createFixtureCopy` from there, a copy of the committed fixture that `changeIt()` rewrites with a version of its own.
- **The embedder.** `startSystem` gives the worker and the server one `Embedder`, as the entry scripts do (`embedder` option). The default is a fake (`test/support/fake-embedder.ts`) that replaces the ONNX session and nothing else: the tokenizer is the real model's, read from `MODEL_PATH`, so a document is cut into the same passages as in production, and the vectors are deterministic and unit length from the token ids of a text, with a model id that says "fake". Every test that is not about how well search ranks uses it, because the real model would embed about 1.7 million characters (about two minutes on one core) in every pull of the fixture. A test that is about citations may use it too, because which documents a citation names does not depend on meaning; it says so beside the test. The tests of ranking pass the real one (`loadRealEmbedder()`, `test/support/real-embedder.ts`), which reads the pinned model from `MODEL_PATH` or `.cache/models/...`. Both fail, naming `npm run model:fetch`, when the model's files are missing, so every seam-1 test needs the model installed. The real-model tests run on an early clock, so that little is embedded (`search.test.ts` embeds about 106,000 characters, 53 passages of 15 documents, in about 6 s on one core; `search-keyword-only.test.ts` about 13,000; measured 2026-10-30), and say why where they do. `test/support/recording-embedder.ts` wraps an embedder to read the passages the worker had it embed, as `olis.documentRequests()` shows what the worker asked OLIS for. The fake is a test double inside seam 1, not a seam of its own. `model:fetch` and `model:verify` are run by hand and in CI, not tested.
- **Entry scripts.** One test file runs `src/bin/ingest.ts` (with `--once`: the schedule's loop is run by `runSchedule`, never as a process with a real timer) and `src/bin/server.ts` as child processes against the fake OLIS, because nothing else executes them.
- **Hermetic.** The suite reaches only localhost. A contract test of the OLIS client against live OLIS is run by hand, outside `npm test`.

## Layout

The layout is the deep-module one in `src/packages/README.md`:

- seam 2 in the parser package's own `tests/` folder, next to the parser it tests (`ingest/tests/schedule.test.ts` is the one table that is not a parser: what runs at a Pacific time, from both settings and what the Session has scheduled, one row for each window edge, setting value, full-pull night and other night, meeting day and day that is not, and both daylight-saving changes; ticket #17, ADR-0039; the table of amendment numbers is in `domain/tests/`, because the domain parses a number where it mints the id);
- seam 1 in `test/tools/`, one file per kind of database use, one line here for each kind (a ticket that adds a test file adds or extends a line of its own, so that two tickets' additions merge without a conflict):
  - `get-measure.test.ts` shares one read-only database and `get-measure-feed.test.ts` builds its own for each case;
  - the live status has `get-measure-live.test.ts` (the fixture as it stands, one pull for each describe, and OLIS answering exactly as the Index), `get-measure-live-feed.test.ts` (what OLIS says after the pull changes, one system for each case), `get-measure-live-changes.test.ts` (what the block says against the top level, pull and read at one clock: unchanged, new entries, a list that differs before its end or is shorter or reordered, a failed lookup; ticket #48, ADR-0038) and `get-measure-live-requests.test.ts` (what the lookup asks OLIS);
  - `get-document.test.ts` shares one database of the whole fixture and `get-document-pull.test.ts` builds its own for each case (fetch counts, failures, rows the fixture lacks);
  - `meetings.test.ts` shares one database at the clock of spec #1's case (c), `meetings-past.test.ts` one at a clock after the whole fixture exists, and `meetings-pull.test.ts` builds its own for each case (another clock, a clock moved after the pull, a failed fetch, a made-up row);
  - `get-measure-analysis.test.ts` shares one database of the whole fixture for the digest and the analysis documents, `get-measure-analysis-labels.test.ts` builds its own for the feed labels the fixture lacks (made-up rows) and `get-measure-analysis-pull.test.ts` builds its own for each case of an analysis document or a Version the worker could not fetch;
  - `compare-amendment.test.ts` shares one database of the whole fixture and `compare-amendment-pull.test.ts` builds its own for each case (made-up postings, files that never came);
  - `get-measure-statute-links.test.ts` shares one database of the whole fixture and `get-measure-statute-links-pull.test.ts` builds its own for each case (the feed as it stood on 2025-02-01, a later pull, made-up Versions);
  - `search.test.ts` shares one database of the early Session (2025-01-17 18:00 Pacific) built with the real model, for paraphrases, citations, Testimony, filters and the shape of a hit;
  - `search-keyword-only.test.ts` builds its own early database with the real model and four made-up rows for agendas, Recording Logs and witness-registration lists;
  - `search-whole-session.test.ts` shares one database of the whole fixture with the fake embedder, for the citations (their cuts are production's, because the fake uses the real tokenizer), the citations the index does not hold, the size of an answer and the values of a hit, which need the late Measures;
  - `search-index.test.ts` builds its own system for each case (passages embedded and reused across pulls, the vector a passage gets, a search in the middle of a pull, a row OLIS changes, an Exhibit OLIS relabels);
  - the two-pull rule of ADR-0005 has `no-longer-listed.test.ts` (one system for each case, read with both kinds of client: a Testimony row the fake stops listing, and the postings of SB 69-2, seen through `search` and `get_document`, on an early clock with the fake embedder; the pulls move the clock an hour or a day at a time so that each has an as-of time of its own), `no-longer-listed-citations.test.ts` (what `search` notes of a cited Proposed Amendment or ORS section that the index holds and the feed no longer lists), `no-longer-listed-unfetched.test.ts` (`get_document` on a row the feed no longer lists, fetched and never fetched, the output schemas' `fetched` descriptions, and the not-held count of analysis documents), `no-longer-listed-lists.test.ts` (one system for each kind of client, changed once: the same rule seen through `testimony`, `meetings`, `get_measure` and a `get_document` on a file never fetched, and, on its own system, the Versions and postings of `get_measure`'s statute links), `pre-listing-database.test.ts` (a database whose rows no complete pull has listed, made with `forgetListing`: every tool serves them as listed), `full-pull-report.test.ts` (what `build-report.json` says of the sets a pull read, of one it refused, of one that is short in a set other than the first and of the schedule sets ConveneTimes and LegislativeSessions, with made-up rows) and `committee-members.test.ts` (made-up rows that share a declared key, read from the build report's committee members);
  - `agency-links.test.ts` shares one database of the whole fixture for the Agency Links `get_measure` shows (each kind of evidence with its count and examples, a parent's link through its sub-unit, the units that are not Agencies, what a citation does not derive, the size of the answer) and `agency-links-snapshot.test.ts` builds its own system for each case of a snapshot that changes between two pulls (a made-up copy of the snapshot fixture with an alias and a version of its own);
  - `statute-links-snapshot.test.ts` builds its own system for each case of the same kind for the Statute Links (a made-up copy of the snapshot fixture with an ORS section inside a range HB 3027 cites and a version of its own: the range, the Agency Links derived from it, a pull of the same snapshot and what the overview reports, and a pull that stops part-way; ticket #51, ADR-0035);
  - `find-measures.test.ts` shares one of the whole fixture for `find_measures` by ORS section, ORS chapter and Agency and for the calls it refuses, `find-measures-since.test.ts` builds a system for each simulated day of spec #1's case (a) (2025-01-24, 2025-01-31, 2025-02-04) and `find-measures-pull.test.ts` builds its own for each case that needs rows the fixture lacks or a feed that moves: made-up Testimony (to page past one page, to cut an item's evidence, to fill a page and measure its size), made-up postings of Proposed Amendments (to date evidence by the postings that hold it, to page across groups, to fill a page with derived evidence), a made-up snapshot (a Department with long-named sub-units), a clock moved before a second pull, and a second pull of the same feed;
  - `search-agency.test.ts` shares one database of the whole fixture, with the fake embedder, for search's Agency filter (it does not depend on how a meaning ranks);
  - where ticket #16 meets tickets #18 and #22, `no-longer-listed-agency-links.test.ts` builds one system, read with both kinds of client before and after the feed stops listing SB 69's Enrolled Version for two complete pulls (`find_measures` flags it, search's Agency filter leaves it out, and `get_measure` shows its flag beside `same_links_as`), `no-longer-listed-agency-evidence.test.ts` builds two systems, read with both kinds of client, one before and after the feed stops listing SB 69's Fiscal Impact Statement 85414 and one after it stops listing Testimony (SB 69's 196915 and a made-up one for SB 983) for two complete pulls (ticket #53, ADR-0037: the document flagged in `get_measure` and `find_measures`, a link with no listed evidence flagged and out of search's Agency filter, a link with other listed evidence unchanged), and `get-measure-same-links-as-table-pull.test.ts` builds one that loads a made-up Statutes Affected Table on its second pull (a Version with the links of the one before it and another table block still says `same_links_as`, ADR-0036) and one with a made-up B-Engrossed Version of SB 69 that the made-up table names (its own block beside `same_links_as`);
  - `increments.test.ts` builds its own system for each case of an increment (a document absent and then found, a row with only a `CreatedDate` and one with only a `ModifiedDate`, the two-hour overlap, `session_overview`'s `last_increment`, and the two-pull rule across an increment; ticket #17, ADR-0039), `ingest-schedule.test.ts` runs the worker's loop through a night, a full-pull night and a meeting day with the harness's sleep (the fake OLIS's request log says what ran) and `staleness.test.ts` builds a system for each case of the warning in each rhythm;
  - `meeting-days.test.ts` builds a system for each case of a day the Session meets, from made-up ConveneTimes and LegislativeSessions rows (a convening-only day, an in-progress weekday, a Saturday, a weekday after the end date, and the staleness warning on each; ticket #67, ADR-0042);
  - `agenda-revisions.test.ts` builds its own system for each case of a revised agenda, read with both kinds of client (an increment and a full pull that fetch it again, its passages replaced in search, a revision number that did not change, one fetch for each new revision; ticket #19, ADR-0041);
  - `hash-sample.test.ts` builds a copy of the whole fixture's system for each case of the nightly hash sample and reads `hash-sample-report.json` (a file swapped behind the same URL, files that are not, the size and the documents drawn, a document OLIS will not give, the next night and a restart, the full-pull night, the night window closing between and during fetches, a mismatch kept across nights; ticket #20, ADR-0040) (`ingest/tests/schedule.test.ts` also holds the hash sample's table);
  - the real-port and entry-script tests are files of their own.
- the shared harness (fake OLIS, clock, MCP client, snapshot) in `test/support/`, with the builders that write the shape of a document's Statute Links as a literal (`statute-links.ts`);
- fixtures in `test/fixtures/`.

Seam 1 and the harness span packages, so they live at the top. Every test imports packages only through their entry points, and dependency-cruiser checks both `src` and `test` for it.

## Speed and property tests

`npm test` should finish in under a minute, so it runs before every commit. The evaluation run against a full local build (#23) has its own script and never runs in `npm test`.

fast-check (`@fast-check/vitest`) covers invariants that tables can't enumerate:

- an expanded ORS range stays inside the snapshot's section list, sorted, with both ends present;
- a parser never throws on arbitrary text.

The real-text tables stay the oracle. A generator built from the parser's own grammar would be a tautology.
