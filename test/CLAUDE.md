# Tests

`/tdd` has the loop and what a good test is. This file has what spec #1 already decided for this repo, and how the harness works.

## The agreed seams

Spec #1 agreed two seams, ticket #23 added a third (the owner approved it on 2026-10-31), and the architecture review of 2026-11-01 added a fourth (the owner approved it that day). Test at these; propose any other seam before writing a test at it.

- **Seam 1: the MCP tools as a black box.** A test starts the fake OLIS at a clock time, runs the ingest worker, and calls tools through an MCP client. It then moves the clock, runs an increment, and calls them again. It asserts what an agent would see.
- **Seam 2: parser tables.** Extracted document text goes in; Statute Links or Agency Links come out. There is one row per wording variant (`test.for`), and each row quotes a real document and names it.

- **Seam 3: the evaluation runner's report.** A built database and a question set (a data file keyed by Session, `scripts/eval/questions/`) go in; one pass or fail for each question, with the reason for each failure, comes out. The runner calls the same MCP tools in-process, so what a question checks is what an agent would see, but the test asserts the report and not the tools' answers, which seam 1 owns. It runs in `npm test` against a copy of the fixture template, where every question passes, and once against a copy changed so that one fails. By command it runs against any built database (`npm run eval`) and never in `npm test`.
- **Seam 4: a deep module's entry point.** A package entry point that holds a rule otherwise spread over storage and its callers (the Snapshot read, the Listing, the Statute Links of a Measure, the tool result envelope, the Index's schema) is called directly, with its real collaborators and, where it stores, a WAL database in a temp directory of its own. No fake OLIS and no MCP client: a case arranges state through package entry points and asserts what the entry point returns or what package entry points read back. It covers the rule's own cases, fast; seam 1 stays the check of what an agent sees, and the seam-1 tests of the rule stay as they are.

Seam-1 tests read state back through the tools, never through tables, SQL or internal types, so storage and ranking can change without touching a test. Seam-2 tests call a parser package's entry point directly: that entry point is the seam. Seam-4 tests read state back the same way, through entry points, never through tables or SQL.

## Expected values

Expected values are literals from an independent source:

- the spec's worked examples, such as HB 3131's 42 Testimony rows (41 support, 1 oppose), or SB 69-2, adopted by SLB on 2025-01-30;
- the Statutes Affected Table;
- the document itself.

## The harness

- **Fake OLIS.** An in-process `node:http` server on `127.0.0.1:0` replays `test/fixtures/` as the feed stood at the clock time. It reproduces the real feed's quirks: `$inlinecount`, 5,000-row pages with a relative `odata.nextLink`, `/$count` answered only without a JSON `Accept` header, misspelled property names, and decimal keys as strings. Its `$filter` is a conjunction of `eq` and `ge datetime'...'` terms, as the live lookup sends, and the increments' parenthesised `(CreatedDate gt datetime'...' or ModifiedDate gt datetime'...')` group (`gt` and `or`, ticket #17), and `FloorLetterId gt 123`, the term an increment reads FloorLetters by (ticket #64); anything else is refused. A test changes it after the pull with `behave` (answer, fail with a status, hang, or drop the connection), `amendRows`, `addRows` and `withholdLastRows` (all sets, or the one set named), and reads the requests it received with `requests()`. An entity set the fixture holds no file for (ConveneTimes, LegislativeSessions, FloorLetters) is served empty, as the real service serves a set with no rows for the Session. To make OLIS stop listing a row, and list it again, a test calls `stopListing` and `listAgain` (`test/support/unlisted-rows.ts`): they move the row to another Session with `amendRows`, so the pull's `$filter` and `$count` leave it out. Because it fakes OLIS at the wire, the OLIS client's quirk handling runs in every seam-1 test, which a mocked OLIS adapter would skip.
  - **Documents.** The feed is always served whole, rows that link documents included. With `documents: true` it also serves the documents themselves, at the paths of the manifest's `source_url`s (`/liz/2025R1/Downloads/...`) on the same port. The worker is pointed at them with `OLIS_DOCUMENT_ORIGIN` (`olis.origin`), so no test reaches the real OLIS: every test that runs the worker sets it, whether or not the files are served (the entry-script test builds the worker's environment in one helper). The files are off by default, because pulling the fixture's 278 documents takes about four seconds and a test of `get_measure` reads none; the fake then answers each document request 404, and the worker lists the document as not fetched.
  - **Counts and failures.** `olis.documentRequests()` lists every document request, so a test reads how often a file was fetched from the harness and never from the database. `documentFailures` makes a chosen document hang past the worker's timeout, or answer a status, before it is served; `strayRows` and `strayDocuments` add a row the fixture lacks, with a fixture file served for it. `madeUpRows` adds MADE UP rows from the start that the `$filter`, the clock and `amendRows` apply to, as to the fixture's (FloorLetters, which the fixture holds none of), and `madeUpDocuments` serves MADE UP bytes at a path from the start whether or not `documents` is on; `test/support/floor-letters.ts` builds both for made-up Floor Letters (ticket #64).
  - **The Statutes Affected Table.** It is not a feed document (no row links it, and it is on www.oregonlegislature.gov), but the fixture's manifest holds it at `/AutoPubs/artables2025R1.pdf` and the fake serves that path like a document, with `documents: true`. `startSystem`'s `statutesAffectedTableUrl` option (`tableUrlOn`, `test/support/statutes-affected-table.ts`) sets the worker's `STATUTES_AFFECTED_TABLE_URL` to it; unset, the worker never asks. A test serves another table from then on with `olis.serveDocument(path, bytes)`, a made-up one built by `madeUpTable` (`made-up-pdf.ts` writes a PDF from lines of text) and labelled so, and withdraws it with `olis.failDocuments(sourceUrl, [404])`. The seam-2 rows are in `statute-links/tests/` (`table-entries.test.ts` for passages of the PDF.js text, `table-fixture.test.ts` for the whole table); the seam-1 files are the ones in `test/tools/` whose names start with `get-measure-statutes-affected-table`, and each header says which cases it holds. `madeUpTablePages` writes a made-up table of several pages with the footer date glued to each page's last row, as PDF.js writes the real one.
- **Clock.** One injected `Clock` drives the fake OLIS, the worker and the server. Global fake timers freeze `performance` for the whole worker, so seam-1 tests move the injected clock instead.
- **Time zone.** The Vitest config sets `TZ` to a zone other than Pacific before workers start. Code that quietly relies on local time then fails.
- **Database.** A WAL file in a disposable temp directory, because WAL can't run in memory.
  - Read-only acceptance cases share one database per file: a copy of the run's template for their options (see Templates), or one built by the file where the pull or the embedder is the subject.
  - Cases that change state (increments, removals, revised agendas) start from a copy of the template for the state before the change, or build their own where the first pull is the subject; the pulls after the change are always real.
  - Keep the two kinds in separate files.
  - **Templates (ticket #47).** A system the suite needs more than once is built once per test run and copied. `startCopiedSystem(options)` and `systemTemplate(options).start()` (`test/support/system.ts`) run the full pull for those options the first time any file asks, checkpoint the WAL into the database file, and keep the files in the run's template folder (`test/support/template-cache.ts`, Vitest's global setup: a new folder for each run, removed at its end). Every case gets a fresh fake OLIS at the same clock and a full copy of the files in a temp directory of its own, so no case can change another's data. The key is a hash of what decides the pull (clock, Session, documents, the fake's rows, the snapshot's bytes, the table's address, the alias file), so two files with the same inputs share one build. A test that passes its own `embedder` is not copied, and neither is a system with the Statutes Affected Table (its address is the fake's origin, which a copy does not share): each file builds those once, as before. A copy's fake OLIS has received no request, so a case that reads `olis.documentRequests()` or `requests()` for the first pull's traffic, or that reads the origin stored in the database (the Statutes Affected Table's `source_url`), pulls for itself.
  - **Which cases copy.** Cases that only read, and cases that change the fake or the clock and then pull again, so that the second pull is the subject and fetches and embeds only what the change adds. That includes every shared read-only file, and the first pull of a case whose second pull (after a moved clock, a changed row or a changed snapshot) is the subject. Each file's header says which of its cases copy.
    - **Rows a case adds.** A case that needs made-up feed rows (and the files they link) but is not about how the pull reads them does not give them to the first pull as `strayRows`. It copies the template of the fixture's pull, adds them with `olis.addRows` and `olis.addStrayDocuments` (the fixture files served at chosen paths, as `strayDocuments` does from the start), and pulls, which fetches and embeds only what it adds. `startCopiedSystemWith(options, { rows, documents })` (`test/support/system.ts`) does the three steps. `get-measure-analysis-labels.test.ts` and the two read-only describes of `compare-amendment-pull.test.ts` do this.
    - **The first pull of a story.** The two-pull rule's cases, `pre-listing-database.test.ts`, `agenda-revisions.test.ts` and `get-measure-live*.test.ts` start from a copy for the state before the change; the pulls after the change, which are the subject, are real. The rule counts from that first pull's listing, which the copy holds.
  - **Which cases pull.** Those whose subject is the pull: increments (the second pull of a case that moves the clock), refused pulls, fetch counts and failures, the pulls of the two-pull rule that come after the change (their first pull is a copy), the Statutes Affected Table's stories, the search index's reuse of passages, and the files whose every case is built from rows of its own (nothing to share). The tests that embed with the real model pull for themselves.
  - A database built before the listing tables is made by `forgetListing` (`test/support/old-database.ts`) after the first pull: it empties `feed_row` and `feed_pull`, which is the state the upgrading worker leaves (it creates the tables empty). It is SQL, used only to arrange; every assertion goes through the tools.
- **MCP client.** Drive `createMcpHandler` in-process through `handler.fetch`, once with a 2026-07-28 client and once with a legacy client. Call `listTools()` first so the client validates `structuredContent`. One test runs on a real port for the Node adapter, the `Host` and `Origin` guards, and the mount path.
- **One system.** `startSystem` (`test/support/system.ts`) starts the fake OLIS at a simulated time, runs the ingest worker's full pull into a temp database and builds the MCP handler, wiring the packages through their entry points the way `src/bin/` does. It refuses to run under the Pacific zone, so a lost `TZ` setting fails loudly. Its `documents` option turns the documents on (default off), `documentTimeoutMs` shortens the worker's wait for a hung document, and the worker never pauses between attempts. `buildReport()` reads the `build-report.json` the worker wrote beside the database. Its `legislatorAliasesPath` option gives the worker an alias file of its own (`test/support/alias-file.ts` writes one), where the entry script passes the committed one. Its `ingest` option sets `INGEST_INCREMENTS` and `INGEST_FULL_PULL` for the worker and the server. Its `incrementAgain()` runs an increment at the clock's time now, and `runSchedule(until)` runs the worker's loop until the simulated clock reaches `until`, its sleep moving that clock (no timer runs; ticket #17). Its `pullAgain()` runs the full pull again after a test moves the clock or changes the fake (for example `olis.withholdLastRows(1)`, so the pull is refused and the test reads the tools to see the index stayed as it was, and `build-report.json` to see which sets were short). `pullAnotherSession(key)` runs the worker's full pull for another Session into the same database, the server still configured for the system's own (ticket #82). `hashSampleReport()` reads the `hash-sample-report.json` of the nightly hash sample (ticket #20); `everyRequestTakes(ms)` makes each request to the fake OLIS move the simulated clock on, so a run is seen to cross a moment; `ingest.hashSampleSize` sets INGEST_HASH_SAMPLE_SIZE and `random` is the randomness the sample draws with (`() => 0`, the first documents by id, unless a test gives another).
- **The snapshot.** `startSystem` gives the worker the committed snapshot fixture (`test/fixtures/oregonai-snapshot/`, ticket #10) as `SNAPSHOT_PATH`; its `snapshot` option gives another path. A test that needs a snapshot with a version of its own writes a made-up one (`test/support/made-up-snapshot.ts`) and says so; a test that pulls twice and changes the snapshot between the pulls takes `createFixtureCopy` from there, a copy of the committed fixture that `changeIt()` rewrites with a version of its own.
- **The embedder.** `startSystem` gives the worker and the server one `Embedder`, as the entry scripts do (`embedder` option). The default is a fake (`test/support/fake-embedder.ts`) that replaces the ONNX session and nothing else: the tokenizer is the real model's, read from `MODEL_PATH`, so a document is cut into the same passages as in production, and the vectors are deterministic and unit length from the token ids of a text, with a model id that says "fake". Every test that is not about how well search ranks uses it, because the real model would embed about 1.7 million characters (about two minutes on one core) in every pull of the fixture. A test that is about citations may use it too, because which documents a citation names does not depend on meaning; it says so beside the test. The tests of ranking pass the real one (`loadRealEmbedder()`, `test/support/real-embedder.ts`), which reads the pinned model from `MODEL_PATH` or `.cache/models/...`. Both fail, naming `npm run model:fetch`, when the model's files are missing, so every seam-1 test needs the model installed. The real-model tests run on an early clock, so that little is embedded (each header gives its amount, measured 2026-10-30), and say why where they do. `test/support/recording-embedder.ts` wraps an embedder to read the passages the worker had it embed, as `olis.documentRequests()` shows what the worker asked OLIS for. The fake is a test double inside seam 1, not a seam of its own. `model:fetch` and `model:verify` are run by hand and in CI, not tested.
- **Entry scripts.** One test file runs `src/bin/ingest.ts` (with `--once`: the schedule's loop is run by `runSchedule`, never as a process with a real timer) and `src/bin/server.ts` as child processes against the fake OLIS, because nothing else executes them.
- **Hermetic.** The suite reaches only localhost. A contract test of the OLIS client against live OLIS is run by hand, outside `npm test`.

## Layout

The layout is the deep-module one in `src/packages/README.md`:

- seam 2 lives in the parser package's own `tests/` folder, next to the parser it tests. `ingest/tests/schedule.test.ts` is the one table that is not a parser (what runs at a Pacific time; ticket #17's agreed seam), and the table of amendment numbers is in `domain/tests/`, because the domain parses a number where it mints the id;
- seam 4 lives in the package's own `tests/` folder, next to the entry point it tests, as seam 2 does;
- seam 1 lives in `test/tools/`, one file per kind of database use. Read-only cases and state-changing cases are in separate files (see Database);
- the names say the kind of database use:
  - `test/evaluation/` holds seam 3: the evaluation runner's report, in one file (`evaluation-runner.test.ts`) whose header says which databases it copies;
  - `<tool>.test.ts` shares one read-only database, a copy of the run's template (exceptions, in a few words: a file whose subject is the real model, the Statutes Affected Table, the clock or the schedule builds its own, and the files for increments, staleness, revised agendas and the listing tables build or copy a system for each case);
  - `<tool>-pull.test.ts` builds its own for each case, where the pull is the subject (exception: a case that only reads or moves a row may copy the template, and some files let one system serve several cases that run in the order written);
  - `<tool>-feed.test.ts` changes the fake feed (rows, clock, page size), after the pull or before it;
  - `no-longer-listed*.test.ts` hold the two-pull rule;
  - the real-port test (`get-measure-http.test.ts`) and the entry-script test (`entry-scripts.test.ts`) are files of their own;
- each test file's header comment says which database it uses (shared and read-only, its own for each case, a copy of a template, a real pull, and why) and what it covers. A new test file is described there, never in this file;
- the shared harness (fake OLIS, clock, MCP client, snapshot) lives in `test/support/`, with the builders that write the shape of a document's Statute Links as a literal (`statute-links.ts`);
- fixtures live in `test/fixtures/`.

Seam 1 and the harness span packages, so they live at the top. Every test imports packages only through their entry points, and dependency-cruiser checks both `src` and `test` for it.

## Timeouts under load

Seam-1 tests pull the fixture, which takes seconds alone and much longer when two suites share a machine (load 30-40 on 2026-10-31 and 11-01: a different set of files timed out at Vitest's 5 s default each time, and each passed alone). `vitest.config.ts` therefore sets `testTimeout` and `hookTimeout` to 60 s for every file, and the worker's pull signal in `startSystem` is 120 s. A test sets no limit below 60 s of its own, because a per-test value overrides the config and brings the old failure back; one that needs more raises it with `vi.setConfig` or a per-test timeout above 60 s. These are limits on a hang, not budgets: a test that waits on a document that hangs shortens that wait with `documentTimeoutMs`, which no timeout here changes.

## Speed and property tests

`npm test` should finish in under a minute, so it runs before every commit. The evaluation run against a full local build (#23) has its own script (`npm run eval`) and never runs in `npm test`; seam 3's test of the runner runs against the fixture, in-process, and takes a few seconds once the templates are built.

fast-check (`@fast-check/vitest`) covers invariants that tables can't enumerate:

- an expanded ORS range stays inside the snapshot's section list, sorted, with both ends present;
- a parser never throws on arbitrary text.

The real-text tables stay the oracle. A generator built from the parser's own grammar would be a tautology.
