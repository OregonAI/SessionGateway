# An analysis document is placed on the Version its label names, and one that the label cannot place is listed as unmapped, never guessed

The feed's `MeasureAnalysisDocuments.Version` is a label, not a Version: it holds nine values in 2025R1, and OLIS does not define them. `get_document` lists the Version an analysis document is of (ADR-0011) and `get_measure` groups a Measure's analysis documents by Version, so one function reads the label for both: `placeAnalysis` in `domain/analysis.ts`. The worker calls it to write the `version` edge, and `get_measure` calls it over the stored edges to group the documents, so the two tools cannot disagree. This takes over the reading of the labels that ADR-0011 ("Version edges") left to this ticket, and narrows it for a row the feed flags `IsMinority`.

The rule reads only what the feed's row says: its label, and its `IsMinority` flag. `INTRO` is Introduced, and a single capital letter is that letter's Engrossed Version (`A` is A-Engrossed), when the feed lists that Version for the Measure (`MeasureDocuments`) and the row is not flagged `IsMinority`. Every other label, a letter whose Version the Measure lacks, and a row the feed flags as a minority report's whatever its label, places the document on no Version. It is still listed, in `analysis_documents.unmapped`, with the feed's label as written and a reason that says what the feed leaves unsaid. Nothing is dropped and nothing is guessed: an agent that reads a Fiscal Impact Statement under the wrong Version tells a director the wrong cost.

All nine labels of the full 2025R1 cache (`.cache/olis-2025R1/feed/MeasureAnalysisDocuments.json`, 5,260 rows, read on 2026-10-30 against its `MeasureDocuments.json`). 4,484 rows are placed on a Version and 776 are listed unmapped:

`IsMinority` is a separate property, and it does not explain `MR*`: its 18 `true` rows are all Staff Measure Summaries and carry `A` (8), `B` (9) and `C` (1). The label of such a row is the letter of the majority's Version, and the feed does not say whether a minority report's summary is of that text or of the minority report's own. Read on the label alone, 10 of the 18 would sit on the majority's Version beside the majority's own summary, with the same type, committee and label: SB 916's 87550 (Staff Measure Summary, SLB, "A", `IsMinority` true), created 11 seconds after 87549 (the same, `IsMinority` false), on a Measure that lists `A-Engrossed` and `Minority Report A-Engrossed`. The 10 are 87550, 89014, 90443, 90753, 90763 (all "A") and 92062, 92071, 92246, 92369, 92607 (all "B"), each with a majority twin of the same Measure, type, committee and label (87549, 89020, 90444, 93901, 90765, 92063, 93903, 92239, 92371, 92608), and each on a Measure that also lists `Minority Report A-Engrossed` or `Minority Report to B-Engrossed`. The other 8 are on a Measure that lacks the Version the label names: 88167 (SB 1098) and 92788 (HB 3908) are "A" on Measures whose Versions include `Introduced`, `Enrolled` and `Minority Report A-Engrossed` but not A-Engrossed; 90733 (HB 2200) is "A" on a Measure whose only Version is `Introduced`; 92164 (SB 951) and 93900 (HB 3409) are "B" on Measures that list `Minority Report to B-Engrossed` but not B-Engrossed; 93832 (HB 2977) and 93847 (HB 3954) are "B" on Measures whose Versions are `A-Engrossed`, `House Amendments to Introduced` and `Introduced`; 93870 (HB 2528) is "C". All 18 are listed unmapped, and their reason says the feed flags them as a minority report's.

## Considered Options

- **Read `B*` as B-Engrossed, and `MRA` as the minority-report Version when the Measure lists one.** This would place 7 more rows, and 16 and 14 more where the Measure has the Version. It is a reading of codes the feed does not define, and it already fails for 4 of 20 `MRA` rows, for 8 of 22 `MRB` rows and for all of `MRC`. The labels stay unmapped until OLIS says what they mean; a mapping then adds a line to `placeAnalysis` and a row to its test.
- **Place a row the feed flags `IsMinority` on the Version its letter names, as the brief's floor does for every other letter.** This is what the first build did. It puts a minority report's summary beside the majority's under the majority's text, where nothing in `get_measure` tells them apart (10 of the 18 rows), on the strength of a label the feed gives for the majority's text.
- **Place a row the feed flags `IsMinority` on the minority report's own Version (`Minority Report A-Engrossed`) when the Measure lists one.** It is the likelier text, and 14 of the 18 rows are on a Measure that lists a `Minority Report` Version; 4 are not (90733, 93832, 93847, 93870). It pairs a flag with a letter to reach a Version name the feed never states, as `MRA` would, and it fails for 4 of the 18 rows. A suggestion is not a mapping: the rows stay unmapped until OLIS says what they are of.
- **Place a blank-label document by its dates or its committee.** A Staff Measure Summary posted between two Versions is not of either by that fact.
- **List only the placed documents.** The ticket asks that an unplaceable document be listed, and an agent that reads "no revenue impact statement" where there is one with an unreadable label is misled.
- **List a document the worker could not fetch, with an id that does not resolve.** It would keep a Measure from reading as having no statement, at the price of the ticket's third box (each entry has an id `get_document` resolves) and of an id an agent cannot follow. A count keeps the box and the Measure's honesty; the id comes back with the next pull that has the file.
- **Store the placement and have `get_measure` read it back.** The `version` edge the worker writes is already the stored placement of a document that has one: the worker wrote it only to a Version the feed lists for the Measure. So `get_measure` runs the same function over that edge, which stands for "the feed lists this Version" for the one Version the document is on and for no other, and the stored label and flag are the only new columns. The edge is not the Measure's list of Versions.

## Consequences

- `get_measure` lists a document only when the worker holds its file, so that every `id` it shows resolves in `get_document`. A document the feed lists and the worker could not fetch is in `build-report.json` (ADR-0011), which an agent cannot read, so `analysis_documents.not_held` counts them: a Measure whose Fiscal Impact Statement timed out reads "1 not held", not "no Fiscal Impact Statement". The worker records which analysis documents the feed lists for each Measure (`analysis_listing`, replaced at every full pull and written before any file is fetched, so that a pull that stops part-way still counts the files it never reached), and the count is the listed ones the store does not hold. The next pull tries them again.
- A group's `version_id` is the id of a Version the feed lists. If the worker could not fetch that Version's file, `get_document` has no document for it, as with the `version` edges ADR-0011 already writes, and the output schema's description of `version_id` says so.
- The worker stores the feed's label and `IsMinority` flag beside each analysis document and refreshes them at every pull, so a label or flag OLIS changes moves the document without fetching it again. A database built before this ADR has no such columns and is rebuilt (no deployment holds one yet).
