# The Statutes Affected Table is set beside the parsed links of the Version each entry names, and a disagreement shows both sides

ADR-0001 adds Legislative Counsel's table as a second source that "confirms or contradicts parsed links" and is "kept side by side, never overwritten". Ticket #22 reads the table (`parseStatutesAffectedTable`, in the `statute-links` package) and `get_measure` shows it. This ADR records what "confirms" and "contradicts" mean and what an agent sees (2026-10-30). Where the table comes from, and when it is read, is ADR-0034.

**An entry names one Version, by its engrossing level.** A row of the table is the Measure with the level it was made from: "SB 69 A" is the A-Engrossed Version of SB 69, "HB 3027" with no letter is the Introduced Version. A single letter names "X-Engrossed" and no letter names "Introduced", the same descriptions the feed gives (`versionDescriptionOfLetter`). A longer level ("BCC", a conference committee report) names no Version in the order Versions are printed in, so nothing is guessed. An “E” alone after the Measure number is read by the Versions the feed lists, and the next paragraph says how. A Version is compared only with the entries that name it. SB 69's Introduced and Enrolled Versions have no table beside them, although the Enrolled text amends the same eight sections as the A-Engrossed: no entry names Enrolled, and the table's reading of "the latest engrossing level" is the table's, not ours.

**An “E” alone after the Measure number is read by the Versions the feed lists.** The legend's “(4) An “E” if an emergency clause applies to the amendment, repeal or addition” and its examples of engrossing levels (“C”, “AMR”, “BCC”) leave an E alone either the emergency clause of a row at the Introduced Version or the level of an E-Engrossed Version, and PDF.js's text, which has no columns, does not say which (`pdftotext -layout` puts the level right after the number and the emergency E in column (4)). The feed's MeasureDocuments rows say which Versions a Measure has, and an E can be a level only if the Measure has an E-Engrossed Version. So (`versionDescriptionOfEntry`):
- When the feed lists no E-Engrossed Version of the Measure, the E can only be column (4). The entry is at the Introduced Version, with the emergency clause, and is compared with the Introduced Version's parsed links as any entry is. This is a deduction from the listed Versions, not a guess, so ADR-0013's rule holds.
- When the feed lists an E-Engrossed Version, the E is either, and nothing is guessed: the entries are shown apart, in `other_entries` with level “E” and no Version, with a reason that says the Measure has that Version, and are never compared with the Introduced Version.
- A Measure the index does not hold shows nothing, as before.

The listing is the feed's, not the index's: a Version whose file the worker could not fetch is listed all the same (`version_listing`, written in each full pull before any file is fetched, as the list of analysis documents is), so a Measure whose E-Engrossed file did not come is not read as having none. The reading is done when `get_measure` answers, from the listing of the last pull, so an E-Engrossed Version that appears after the table was loaded changes the answer and the table is not read again. The first build of this ticket read every E alone as the emergency clause; the second (finding F4) left every one unknown. 2025R1's feed lists no E-Engrossed Version of any Measure (none of its 6,178 MeasureDocuments rows; its latest level is C), and 819 entries of its table end in an E alone, for 180 Measures (counted on 2026-10-30 with the parser, a series not expanded; 836 lines of its ORS pages end that way in a regex count over the PDF.js text), none a Measure of the fixture: all of them are read as the emergency clause of the Introduced Version, and none is unknown. The build report counts them for a table it loads: `lone_e_entries`, and `lone_e_with_e_engrossed_version`, the ones left unknown (0 for 2025R1).

**What follows the Measure number is read by the table's legend.** Page 1 of the table says: “(b) The section number and current session measure number or previous session measure number if a measure was repassed over the Governor’s veto, followed by “OV” for a current session overturned veto or “OVP” for a previous session overturned veto”, “The engrossing level is printed next to the measure number”, and “(4) An “E” if an emergency clause applies to the amendment, repeal or addition” (the text the pdf-text package extracts, lines 11-13, 17 and 25). So a tail holds at most one engrossing level, one veto mark and an "E" last, and the parser tells them apart by what they say, because the legend does not say whether the level or "OV" comes first. A row with "OV" is this Session's Measure, read by its level as any other. A row with "OVP" is a previous Session's Measure that shares a number with nothing in this index: it is kept apart in the parse (`previousSessionEntries`), counted in the build report (`previous_session_entries`), never stored as an entry and never shown under this Session's Measure of that number; its continuation rows still follow its ORS number. A tail the legend has no form for (two levels, two veto marks, an "E" before a veto mark, four tokens) leaves the line unread, and the continuation rows after an unread line are unread too, until a row with its own ORS number: they belong to the number that line printed, which is not known.

**What is compared is a kind, a target and a measure section.** The table's "A" is a link that amends, its "R" repeals and its "Add" adds to (`statuteLinkKindOfTableAction`). A parsed link and an entry agree when kind, ORS target and measure section are all equal; the section is compared as the text prints it ("8", "93a"), and a parsed link whose text has no numbered sections (`null`) agrees with no entry. Citations are never compared: the table does not list them, so a parsed `cites` link is neither confirmed nor a disagreement.

**What `get_measure` shows.** With a table held, each Version some entry names gets a `statutes_affected_table` beside its `statute_links`, in #13's compact form (by kind, each target once with its measure sections, ORS sections and chapters apart, a chapter marked `resolvable_on_oregonai: false`), with no `cites`. Nothing in it is listed twice, and no list repeats the table's whole `entries`:
- `parsed_changes`: each parsed link that amends, repeals or adds to, once, with `confirmed_by_table: true` when the table has an entry for it (the same kind, target and measure section) and `false` when it has none. A target the table confirms in one measure section and not in another is listed once for each.
- `only_in_table`: the disagreements on the table's side, the entries the parsed links lack.
- `only_in_parsed_links`: the disagreements on the text's side, the parsed links that change the law and have no entry (the `confirmed_by_table: false` targets of `parsed_changes`).
- `compared`: false, with the reason, when this index did not read the Version's text (a scan, or a file not read yet). `parsed_changes`, `only_in_table` and `only_in_parsed_links` are then null, and `entries_not_compared` holds the table's entries for the Version, because an empty list would otherwise read as "the text says nothing". It is null when `compared` is true.
- A list with nothing in it is null, and a list that can grow with a series (a series is one entry for each section of it) shows its first twenty sections and its first twenty chapters, with `sections_not_shown` or `chapters_not_shown` saying how many it left out. HB 3027's series of 22 sections is shown as twenty and "2 not shown". The Version's `statute_links` are not cut: they are #13's.

A disagreement is never resolved: a table entry that says 653.616 is repealed in §8 while the text amends it in §8 is in `only_in_table` as a repeal and in `only_in_parsed_links` as an amendment, each as its source has it. The parsed `statute_links` of the Version are the same with or without the table. At the level of `statute_links_by_source`, `statutes_affected_table` says where the table came from (`source_url`) and when this index retrieved it (`retrieved_at`), whether it lists the Measure at all (`lists_measure`), and `other_entries`: entries that name a Version this index does not hold, or a level that names none, as the table prints them (cut like the lists above) and compared with nothing. A Measure the table has no entry for has `lists_measure: false` and nothing beside any Version: the table's silence is not read as a claim about a Version, because it does not say which Version it would have named. When this index holds no table, neither field is present and the answer is the one `get_measure` gave before the ticket.

**A series is expanded where the text's ranges are.** The table prints "9.005 to 9.757 Add §1 SB 880" as two lines with a brace between them, and a continuation row of the series omits the target again. The worker expands the series with the snapshot's ORS section list, the way `parseStatuteLinks` expands "ORS 345.010 to 345.340" (HB 3027's Introduced Version and its table row give the same 22 sections), and a series of chapters ("Ch. 71 to Ch. 79") into its two chapters and the chapters of the list between them. The series is expanded once, when the table is read, so a deployment that changes its snapshot rebuilds, as ADR-0015 says for the links.

## Considered Options

- **Mark each parsed link as confirmed inside `statute_links`.** It keeps the table out of a second block, but a target linked in two measure sections can be confirmed in one, and it reshapes the form #13 and ADR-0015 settled after review.
- **Repeat the table's `entries` beside `confirmed` and the disagreements.** The first build listed every entry of the Version, then the confirmed ones, then the ones only in the table, so each entry stood in two or three lists: +2,558 characters for SB 69's `get_measure` (65,272 without the table, 67,830 with it) and +3,852 for HB 3027. The flag on `parsed_changes` says the same once.
- **One flat object for each link, entry or disagreement.** Rejected for the reason ADR-0015 gives: SB 1111 has 239 entries in the table (counted by the parser on 2026-10-30, series not expanded), SB 164 has 182, and a flat object for each would repeat the target, the kind and the section in every one.
- **Read every E alone as the emergency clause (the first build).** It compares an E-Engrossed Version's entries with the Introduced Version's links whenever a Measure has been E-engrossed, a false disagreement that nothing in the table could correct.
- **Leave every E alone unknown (finding F4's build).** It never guesses, but 2025R1's feed lists no E-Engrossed Version at all, so it lost the comparison for about 180 Measures to guard against a Version none of them has.
- **Decide from the Versions the index holds.** Simpler (no listing), but a Measure whose E-Engrossed file did not come would be read as having none, and its E alone compared with the Introduced Version: a deduction from a premise that is not true. The feed's listing is the premise.
- **Compare every Version that has the same text.** The Enrolled Version of a chaptered Measure is the named engrossed Version's text with its engrossing corrections, but the table does not say so and the ticket compares "the Version an entry names". The owner can widen it (see the questions in the pull request).
- **Count a Measure the table lists nothing for as a disagreement for every Version with changing links.** The table covers a Measure at its latest level only, so an earlier Version's links are not contradicted by its silence.

## Consequences

- The fixture's table agrees with every Version it names (checked for all eighteen Versions of the fixture's Measures: SB 69 A-Engrossed 9 of 9 rows, HB 3795 B-Engrossed 2 of 2, SB 983 A-Engrossed 1 of 1, HB 3027 Introduced 22 of 22 sections of one series), so a real disagreement is not in the fixture and the seam-1 tests serve a made-up table for the cases a disagreement needs.
- The table's rows for SB 69 are nine, not the three the ticket names (653.616 §8, Ch. 657B §1, 659A.159 §4): the table also prints 653.626 §9, 657B.060 §7, 657B.070 §3, 657B.400 §6, 659A.156 §10 and 659A.165 §5, and all nine are in the seam-2 test and in `get_measure`.
