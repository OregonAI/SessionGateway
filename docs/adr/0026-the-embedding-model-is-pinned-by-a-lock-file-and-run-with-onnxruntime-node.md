# The embedding model is pinned by a lock file, fetched by a script, and run with onnxruntime-node and @huggingface/tokenizers

ADR-0006 picks bge-small-en-v1.5. This ADR records how the files reach a machine and what runs them (ticket #9).

**The files.** `Xenova/bge-small-en-v1.5` at revision `ea104dacec62c0de699686887e3f920caeb4f3e3` is BAAI/bge-small-en-v1.5 (MIT) converted to ONNX; the Xenova repository states no licence of its own. The service reads five of its files: `onnx/model_quantized.onnx` (q8, 34,014,426 bytes), `tokenizer.json`, `tokenizer_config.json`, `special_tokens_map.json` and `config.json`. `src/packages/embedder/data/model-lock.json` names the repository, the revision and each file's size and sha256; the values were copied from the manifest of the install the lead made and checked against the Hugging Face tree at that revision.

**The scripts.** `npm run model:fetch` (`scripts/model/fetch.ts`, no dependency but `node:` built-ins) downloads each file that is missing or wrong from `https://huggingface.co/<repo>/resolve/<revision>/<path>` into `.cache/models/<repo with / as -->/<revision>/`, checks its size and sha256 before moving it into place, and sends no request for a file that is there and verified. `npm run model:verify` checks the same offline, names every missing or changed file, and is a step of `npm run check`. Both read `MODEL_PATH` when it is set, so a deployment verifies the directory it runs from. The directory is gitignored. CI caches `.cache/models` with `actions/cache` keyed on the lock file and runs `model:fetch` before `npm run check`; on a hit `model:fetch` checks the files and sends nothing. The tests read the model through `MODEL_PATH` or that default directory and fail with a message that names `npm run model:fetch` when it is missing.

**The runtime.** `onnxruntime-node` 1.30.0 (MIT) runs the model on the CPU and `@huggingface/tokenizers` 0.2.0 (Apache-2.0, no dependencies) tokenizes. `@huggingface/transformers` was not used: it depends on `sharp`, whose `@img/sharp-libvips-*` binaries are LGPL-3.0-or-later, and a licence exception for a pipeline the service uses a small part of is not worth it. 1.31.1 of onnxruntime-node is younger than the 14 days `.npmrc` allows.

**The install script is denied** (`allowScripts`: `"onnxruntime-node": false`). It runs `node ./script/install`, which on linux/x64 downloads three CUDA execution-provider libraries (`libonnxruntime_providers_cuda.so`, `_shared.so`, `_tensorrt.so`) from NuGet; on every other platform it downloads nothing. The service runs on the CPU, and the CPU runtime is in the package: with the script denied, the model loads and embeds (checked 2026-10-30). The package is 301,068,136 bytes unpacked (294,188 KiB on disk), 45.8 MB of it for linux/x64 (`libonnxruntime.so.1` and the binding); darwin, win32 and linux/arm64 are 86, 134 and 25 MB that the image (#25) can leave out. Its dependencies are `adm-zip`, `global-agent` (BSD-3-Clause) and `onnxruntime-common`, used by the install script and not at run time; the licence check passes on all 15 packages added.

**The tokenizer package's types do not resolve** under `module: nodenext`: its declarations import their own files without an extension. `tsc` hides the failure (`skipLibCheck`) and treats the class as untyped, so ESLint's `no-unsafe-*` rules reject every use of it. `embedder/lib/tokenizer.ts` is the one file that names the package and types the part the embedder uses; no rule is silenced.

**What the embedder does.** `embedder/index.ts` is the interface (`Embedder`: a model id, a token count, passage vectors and a question vector), and `embedder/onnx.ts` the real implementation; the entry scripts make one from `MODEL_PATH` and pass it down, as they do the clock, and the tests pass a fake (`test/support/fake-embedder.ts`, whose model id says "fake"). A text is run alone and never in a batch: the quantized model scales its activations over the whole tensor it is given, so a passage run with others gets a slightly different vector from the one it gets alone (cosine 0.9977 for a 12-token passage beside another of 12, measured in the review of #9), and a vector that is kept under the hash of its text and reused must be a function of that text. One thread gains no speed from a batch, and a batch raises the peak memory (eight passages of 510 tokens: 440 MB in a batch of 8, 266 MB one at a time, in the same review). Measured 2026-10-30 on one thread: the model loads in 115–128 ms; a server process is listening 304 ms after it starts, with the model loaded; a question takes a median 5 ms (30 runs, max 7 ms); a passage of 288 tokens takes 4,200 tokens/s in batches of 16; resident memory is 62 MB for bare Node, 93 MB with `onnxruntime-node` imported, 194 MB with the model loaded, and the server's was 228 MB once listening and 251 MB after 24 searches over the fixture.

## Considered Options

- **transformers.js,** as the research ran it. Needs `sharp` and an LGPL exception.
- **Vendoring the model in the repository.** 34 MB of weights in every clone for a file the lock already pins.
- **Downloading at start-up.** A public server that reaches a third party every time it starts, and a start-up that can fail on someone else's outage.
- **Approving onnxruntime-node's install script.** Fetches 400 MB of GPU libraries the service never loads.
