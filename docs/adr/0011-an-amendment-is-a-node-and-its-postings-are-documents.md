# A Proposed Amendment is one node, each of its postings is a document, and a pull records the feed before it fetches files

Spec #1 makes a Proposed Amendment "one node per Measure and amendment number, with one posting edge per meeting it appeared at", and keeps each document when the text differs between postings. The feed has one `CommitteeProposedAmendments` row for each posting, and each row has a file of its own: SB 69's -1 has three rows and three files, and the files differ (the PDF's modification date, in the fixture; the words, whenever a committee revises an amendment and posts it again).

So the node is `amendment-2025r1-sb69-1` and each posting is a document, `posting-2025r1-26284`, by the feed's `ProposedAmendmentId`. A posting points at its meeting with a `posted_to` edge that carries what the committee did there (the feed's `Meaning`: Proposed, Adopted) and at the node it is a text of. `get_document` on the node serves the text of its latest posting (by meeting, then by id) and lists every posting's meeting with the document posted there; `get_document` on a posting serves that posting's text. A revised amendment therefore never replaces the text a committee saw at an earlier meeting, and the node's id stays the one an agent cites.

Other decisions that agents see, because the ids and shapes are cited and so hard to change:

- **Ids.** A Version is `version-2025r1-sb69-a-engrossed` and a Printed Amendment, whose description names "Amendments" ("Senate Amendments to Introduced"), is `printed-amendment-2025r1-sb69-senate-amendments-to-introduced`. A `CommitteeMeetingDocuments` row of type "Recording Log" is `recording-log-2025r1-<id>`; every other row is `exhibit-2025r1-<id>`. An agenda is `agenda-2025r1-slb-2025-01-30-0800`, named like its meeting. The feed writes one amendment number with a trailing space ("-2 "); numbers are trimmed.
- **Version edges.** `get_document` lists the Version a document is of: an analysis document points at the Version its feed row's `Version` label names, and a Printed Amendment at the Version its own description names ("Senate Amendments to A-Engrossed" amends A-Engrossed). Only the unambiguous labels are read: "INTRO" is Introduced and a single letter is that letter's Engrossed Version ("A" is A-Engrossed). Blank labels and the ones more than one description could answer ("B*", "MRA", ...; `docs/research/olis-odata.md` gotcha 9) name no Version, and neither does a label for a Version the feed does not list for that Measure: an edge to a document that is not there is worse than none. Reading the labels for a Measure's whole list of Versions (`get_measure`) is a later ticket's, and it may widen this reading.
- **Parts.** `get_document` takes an id and a part number from 1, and every part says how many there are. A part is at most 20,000 characters, about 5,000 tokens at four characters to a token (the rule of thumb of `docs/research/olis-odata.md` section 7, inferred): a few percent of an agent's context, so a 300-page document costs several small results and not one that crowds out the conversation. The longest fixture document, a 94-page letter, is 20 parts. A part ends at the end of a line, and the parts joined are the text exactly.
- **Text layer.** A file that yields only whitespace has no text layer; its text is empty and `has_text_layer` is false (ADR-0010).
- **The build report.** After a full pull the worker writes `build-report.json` beside the database, with every stored document that has no text layer and every document it could not get or read, each with its id and `source_url`. It is a file for the operator: the list can run to hundreds of documents on a whole Session, too long for every agent's `session_overview`, which carries the count.
- **Order of a pull.** A full pull reads the whole feed, records Measures, committees, meetings and the as-of time, brings what the feed now says about the documents it already holds (their label, the nodes they point at, a posting's Meaning) up to date without fetching them, and then fetches the files it does not hold. The file is unchanging (ADR-0005) but its row is not: OLIS changes a posting's Meaning and a Testimony's Measure after the fact, and a stale edge would tell an agent that an adopted amendment was only proposed. The as-of time therefore means the feed was read, not that every file is in; a crash during the hours of a first pull keeps the feed and every file fetched so far, and the next pull fetches the rest. A file that is missing, timed out three times, or is not a PDF is left out and reported, and the next pull tries it again. Only a file that PDF.js reports as not a PDF (`InvalidPDFException`) counts as "not a PDF": any other failure of the extractor (a bundle that cannot load, a PDF.js bug, running out of memory) is a bug or a broken machine, and it stops the pull with an error that names the document. A file that trips such a bug therefore stops every pull at that file until someone looks, which is loud on purpose.

## Considered Options

- **Key the node's one document by amendment number and keep only the latest file.** Simpler, but it loses what was posted to the earlier meeting, which is what an agent preparing for a hearing needs.
- **Give each distinct text its own id and the node an alias.** The same documents as postings, but the id would depend on a content comparison that a later posting can change.
- **Put the build report in `session_overview`.** One place for agents and operators, but a list of hundreds of ids in a tool result every agent reads.
- **Record the as-of time after the last file.** Honest about files, but a first pull of 132,000 documents would leave the server with no as-of time for days.
