# `find_measures` lists items in groups by how they are tied, dates them by the row's created time, and `since` reads the latest posting

Ticket #16 builds `find_measures` and search's Agency filter. Spec #1 says what they do ("Measures, Versions and Proposed Amendments with Statute Links or Agency Links to a given Agency, ORS section or ORS chapter, optionally only items posted since a time"). The ticket and the brief leave the following to this ADR.

**An item is a node.** The Measure, a Version, or a Proposed Amendment (ADR-0027 says which node each link sits on), with its Measure, its `source_url` (the Measure's OLIS page, the Version's file, or the file `get_document` serves for the amendment: its latest posting), and its evidence. For an Agency the items come in four groups kept apart, because the acceptance box asks for the first two separately: those that touch its statutes (derived), those that name it in a Fiscal Impact Statement, those that name it in their text, and Testimony. An item is in each group it is tied in. For an ORS section or chapter there is one group, the Versions and Proposed Amendments with a Statute Link to it of any kind, citations included, each target one piece of evidence under its kind with the measure sections it is read in. A chapter takes the links to the chapter and to any section in it (`ors-657b.` up to `ors-657b/`, so chapter 657 does not take chapter 657B's sections). A Proposed Amendment is listed with its links whether or not a later Version replaced them (ADR-0015 hides them in `get_measure`): "what was posted since yesterday" is a fact about the posting.

**Posted time is the feed's `CreatedDate`.** For each document the feed links, the OLIS client reads the row's `CreatedDate` (a Version's `MeasureDocuments` row, a posting's `CommitteeProposedAmendments` row, a statement's `MeasureAnalysisDocuments` row, a Testimony's `CommitteePublicTestimonies` row), and the worker keeps it in `document_created` with the rest of the feed's listing, before any file is fetched, so a posting whose file did not come still has its time. An item's time comes from the evidence that makes it an item: the Version's row for a Version's text and Statute Links, the postings' rows for a Proposed Amendment's, the statement's row for a Fiscal Impact Statement's link (a Version listed there for the statement is not dated by its own row), the Testimony's row for Testimony. `posted_at` is the earliest such time and `last_posted_at` the latest.

**`since` is compared with the latest.** The brief dates a Proposed Amendment by "its earliest posting" and expects the result for 2025-01-23 to hold SB 69-1 and -2. They cannot both hold: -1's first posting, 26284, was created on 2025-01-17 (feed/CommitteeProposedAmendments.json), and it was posted again to two later meetings, 26285 and 26287, on 2025-01-23. A staffer asking what was posted since yesterday must see that -1 was posted again, so `since` is compared with `last_posted_at`, and `posted_at` stays the earliest posting as the brief says. For everything but a Proposed Amendment posted more than once the two are the same time. An item with no time (a row the feed gave no `CreatedDate`) is left out when `since` is given.

**`since`** is a date (midnight Pacific), a time with no offset (Pacific), or a time with an offset, and the answer says the time it read, in Pacific time with its offset. The feed's times are Pacific wall-clock readings that the OLIS client gives their offset (spec #1, "OLIS client"), so a comparison is by instant.

**Size.** The answer is a page of 50 items counted across the groups in their fixed order (derived, Fiscal Impact Statement, text, Testimony; each group newest first, then by id), with every group's total, and `page`, `last_page` and `page_size` like `testimony`. An item lists at most ten pieces of evidence and says `evidence_total`: a Measure can have dozens of Testimony from one Agency. Measured 2026-10-30 over the whole fixture, an item is 650 to 900 characters, so a full page is 33,000 to 45,000, between one and a half and two parts of `get_document`.

**Errors and notes.** Giving none or more than one of `agency`, `ors_section` and `ors_chapter`, an Agency that is not a slug, a section or chapter in no form this reads, a `since` that is no time, and a page past the last are tool errors. An Agency slug or an ORS target the index holds no link to is an answer with no items and a note that says so: the server has no registry to tell a typo from an Agency that no Measure touches. An item whose own row the feed no longer lists (the Measure's, the Version's, or every posting of the Proposed Amendment's: two complete full pulls in a row have missed it, ADR-0030) stays in its groups with `no_longer_listed: true`, as every tool that lists rows keeps such a row; an item the feed lists has no flag.

**search's Agency filter** keeps the hits whose Measure has an Agency Link of any evidence to the Agency (the Measures of `agency_link` through a document, and of `testimony`). A document that belongs to no Measure (an agenda, a Recording Log) is left out. The filter is applied to the keyword side in SQL and to the vector scan in memory, like the other filters, and a slug no link names gives no hits and a note. A document the feed no longer lists (ADR-0030) is left out of every query and of the vectors whatever the filters, so the Agency filter never brings one back.

## Considered Options

- **Date an amendment by its earliest posting**, as the brief says. An amendment first posted a week ago and posted again yesterday would not be "posted since yesterday".
- **Date each item by its own row for every group.** A Fiscal Impact Statement is posted when the statement is, not when the Version it is of was: SB 69's statement was created on 2025-01-30 and its A-Engrossed Version on 2025-02-03.
- **One item for each posting of a Proposed Amendment**, or for each Testimony. The amendment is one node (ADR-0011), and a Measure with thousands of Testimony would fill the pages.
- **Compare times in SQL**, which would need the offset in the string to compare right across the changes to and from daylight time. The items an Agency has are filtered and sorted in the tool, with `Temporal`, which does.
- **A tool error for a slug no link names.** It would also refuse an Agency that exists and that no Measure touches yet.

## Consequences

- A database built before this ticket gets the new tables from the worker's schema at its next pull, which then reads every stored document for Agency Links and records every document's created time. No database has been deployed (tickets #24 and #25), so a rebuild is the other answer.
- The tool reads every link of an Agency to sort and page them. For the Departments with the most links in the whole Session that is thousands of rows and some tens of milliseconds; if it grows, the sort and page move into SQL.
- `since` has no upper bound, and "yesterday" is the caller's: the tool never reads the clock.
