# `find_measures` lists items in groups by how they are tied, dates their evidence by the created time of the documents that hold it, and `since` reads the latest

Ticket #16 builds `find_measures` and search's Agency filter. Spec #1 says what they do ("Measures, Versions and Proposed Amendments with Statute Links or Agency Links to a given Agency, ORS section or ORS chapter, optionally only items posted since a time"). The words "posted since" are the spec's; this service's time for them is the feed's created time (GLOSSARY.md, "Created time"), because "posted" is what a Proposed Amendment's posting to a meeting is, and a meeting's time is another time. The ticket and the brief leave the following to this ADR.

**An item is a node.** The Measure, a Version, or a Proposed Amendment (ADR-0027 says which node each link sits on), with its Measure, its `source_url` (the Measure's OLIS page, the Version's file, or the file `get_document` serves for the amendment: its latest posting), and its evidence. For an Agency the items come in four groups kept apart, because the acceptance box asks for the first two separately: those that touch its statutes (derived), those that name it in a Fiscal Impact Statement, those that name it in their text, and Testimony. An item is in each group it is tied in. For an ORS section or chapter there is one group, the Versions and Proposed Amendments with a Statute Link to it of any kind, citations included, each target one piece of evidence under its kind with the measure sections it is read in. An item's evidence is grouped by kind, each kind with its `count`, how many the cut `left_out`, and its newest `examples`; the documents the examples name are listed once in `documents`, with their `source_url`, as `get_measure`'s `agency_links` does (ADR-0027). A chapter takes the links to the chapter and to any section in it (`ors-657b.` up to `ors-657b/`, so chapter 657 does not take chapter 657B's sections). A Proposed Amendment is listed with its links whether or not a later Version replaced them (ADR-0015 hides them in `get_measure`): "what was posted since yesterday" is a fact about the posting.

**The created time is the feed's `CreatedDate`.** For each document the feed links, the OLIS client reads the row's `CreatedDate` (a Version's `MeasureDocuments` row, a posting's `CommitteeProposedAmendments` row, a statement's `MeasureAnalysisDocuments` row, a Testimony's `CommitteePublicTestimonies` row), and the worker keeps it in `document_created` with the rest of the feed's listing, before any file is fetched, so a posting whose file did not come still has its time. A piece of evidence is dated by the documents whose own file holds it, and by no other: a Version's or a statement's or a Testimony's own row, or, for a Proposed Amendment posted to several meetings, each posting whose file gives the same link (the same file, or a file that reads the same). A posting of a different file never dates evidence it does not hold: SB 69-1 posted again with another amendment's text on a later day is not "posted since" that day for the Bureau (fix pass of #16, F2). A posting whose file did not come holds nothing known, so it dates nothing. An item's `created_at` is the earliest and `last_created_at` the latest of the times of its evidence. (Fix pass of #16, F16: the fields were `posted_at` and `last_posted_at`, and the glossary's term "Posted time", which is also what `DocumentLink.postedAt`, the time of the meeting, would be called.)

**`since` is compared with each piece of evidence's latest posting.** The brief dates a Proposed Amendment by "its earliest posting" and expects the result for 2025-01-23 to hold SB 69-1 and -2. They cannot both hold: -1's first posting, 26284, was created on 2025-01-17 (feed/CommitteeProposedAmendments.json), and it was posted again to two later meetings, 26285 and 26287, on 2025-01-23, with a file that reads the same. A staffer asking what was posted since yesterday must see that -1 was posted again, so a piece of evidence is "posted since" when the latest document that holds it was created at or after `since` (`since` filters on `created_at`), and `created_at` stays the earliest posting as the brief says. With `since`, an item lists only the evidence created at or after it, and its `created_at` and `last_created_at` are those of that evidence; the cut keeps the newest first and says how many it left out (fix pass of #16, F4: a cut by document id had hidden the one Testimony posted since). An item with no evidence left is not an item, and a piece with no time (a row the feed gave no created time) is left out when `since` is given.

**`since`** is a date (midnight Pacific), or an ISO 8601 or RFC 9557 time with "T" or a space between the date and the time: with an offset or "Z" it is that instant, with a zone in brackets and no offset it is that zone's wall clock, and with neither it is Pacific. The time package reads it with Temporal's own parsers (`readTimestamp`; fix pass of #16, F1 and F13): `Temporal.PlainDateTime.from` drops an offset without a word, so it is tried last, on a text that has none. The answer says the time it read, in Pacific time with its offset. The feed's times are Pacific wall-clock readings that the OLIS client gives their offset (spec #1, "OLIS client"), so a comparison is by instant.

**Size.** A page of `find_measures` is bounded like a page of `testimony` (about 25,000 characters, a little over one part of `get_document`), with a full page and every item at its evidence cap (fix pass of #16, F6). The cap is three examples of evidence for an item, the newest first, across its kinds; a page is 12 items counted across the groups in their fixed order (derived, Fiscal Impact Statement, text, Testimony; each group newest first, then by id), with every group's total, and `page`, `last_page` and `page_size`. A derived link through sub-units shows the first two and `through_total`, because a Department can have many (Agriculture has 24 in the registry, 22 of them implementing chapter 192). Measured 2026-10-30 on full pages of made-up rows (test/tools/find-measures-pull.test.ts), which before the change were pages of 50 items with ten pieces of evidence each:

| A full page of | Before (50 items, ten pieces) | After (12 items, three examples) |
|---|---|---|
| Testimony, from the Organization with the longest name (96 characters), 12 rows on each Measure | 156,584 | 17,580 |
| Derived links of the Bureau of Labor and Industries, three chapters each | 62,057 | 14,888 |
| Derived links of the Department of Human Services, through one 94-character sub-unit | 38,555 | 11,190 |
| Derived links of a made-up Department, through five 94-character sub-units, three chapters each | not measured | 22,937 |

An item with its three examples is about 900 to 1,900 characters (the pages above divided by 12). What the cap does not bound is the length of a field of one example (a `unit`, the `terms` found, a list of `measure_sections`), which the registry and the bill bound instead; the largest case a registry can give, the last row above, is the one the page size is chosen for.

**Errors and notes.** Giving none or more than one of `agency`, `ors_section` and `ors_chapter`, an Agency that is not a slug, a section or chapter in no form this reads, a `since` that is no time, and a page past the last are tool errors. An Agency slug or an ORS target the index holds no link to is an answer with no items and a note that says so: the server has no registry to tell a typo from an Agency that no Measure touches. An item whose own row the feed no longer lists (the Measure's, the Version's, or every posting of the Proposed Amendment's: two complete full pulls in a row have missed it, ADR-0030) stays in its groups with `no_longer_listed: true`, as every tool that lists rows keeps such a row; an item the feed lists has no flag.

**search's Agency filter** keeps the hits whose Measure has an Agency Link of any evidence to the Agency (the Measures of `agency_link` through a document, and of `testimony`). A document that belongs to no Measure (an agenda, a Recording Log) is left out. The filter is applied to the keyword side in SQL and to the vector scan in memory, like the other filters, and a slug no link names gives no hits and a note. A document the feed no longer lists (ADR-0030) is left out of every query and of the vectors whatever the filters, so the Agency filter never brings one back.

## Considered Options

- **Date an amendment by its earliest posting**, as the brief says. An amendment first posted a week ago and posted again yesterday would not be "posted since yesterday".
- **Date each item by its own row for every group.** A Fiscal Impact Statement is posted when the statement is, not when the Version it is of was: SB 69's statement was created on 2025-01-30 and its A-Engrossed Version on 2025-02-03.
- **One item for each posting of a Proposed Amendment**, or for each Testimony. The amendment is one node (ADR-0011), and a Measure with thousands of Testimony would fill the pages.
- **Compare times in SQL**, which would need the offset in the string to compare right across the changes to and from daylight time. The items an Agency has are filtered and sorted in the tool, with `Temporal`, which does.
- **Pages of 50 with ten pieces of evidence each**, as the ticket says of `testimony`. The first design; the review measured a page at 120,000 to 168,000 characters (the table above).
- **A cap on the size of an item's JSON** rather than a count of examples. It needs a rule for what to cut first, and a count is what an agent can read ("3 of 12").
- **A tool error for a slug no link names.** It would also refuse an Agency that exists and that no Measure touches yet.

## Consequences

- A database built before this ticket gets the new tables from the worker's schema at its next pull, which then reads every stored document for Agency Links and records every document's created time. No database has been deployed (tickets #24 and #25), so a rebuild is the other answer.
- The tool reads every link of an Agency to sort and page them. For the Departments with the most links in the whole Session that is thousands of rows and some tens of milliseconds; if it grows, the sort and page move into SQL.
- `since` has no upper bound, and "yesterday" is the caller's: the tool never reads the clock.
- Every Proposed Amendment node a call meets is looked up by its node id in `meeting_document` (its number, from its earliest posting), and the table had only a `meeting_id` index, so each lookup scanned the table: 16,115 rows in the full 2025R1 cache, 3,134 of them postings of Proposed Amendments (docs/research/olis-odata.md). `meeting_document_node` on `node_id` makes it a search (fix pass of #16, F8; `EXPLAIN QUERY PLAN`, before: `SCAN md`, after: `SEARCH md USING INDEX meeting_document_node (node_id=?)`, on the fixture's database as well as an empty one). The second lookup the review measured, the postings' created times, went with F2: an item is dated by the documents that hold the evidence, which the query for the evidence already returns.
