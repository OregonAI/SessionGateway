# The Statutes Affected Table is fetched from a URL the deployment names, read again only when its bytes change, and kept when the server stops giving it

The table (`artables{session}.pdf`) is Legislative Counsel's, on `www.oregonlegislature.gov`, not OLIS's: no feed row links it, and it does not exist until the Session has ended (2025R1's is dated 8/19/2025; ADR-0001). The worker therefore cannot learn its address from the feed. Ticket #22 gives it to the worker as `STATUTES_AFFECTED_TABLE_URL` (2026-10-30), read through the config module like every other variable: an `http` or `https` URL, or unset. A bad value stops the worker at start-up and names the variable, never its value.

- **Unset: nothing happens.** The worker makes no request for the table, writes no word about it in the build report, and `get_measure` is as it was before the ticket.
- **Fetched in each full pull.** The worker fetches the address with the retries a document gets (a transient failure is tried again, a 404 is not) and takes the sha256 of the bytes. When it equals the hash of the copy the index holds, the table is not extracted or parsed again. Otherwise the worker extracts the text with the pdf-text package (ADR-0010), parses it with the snapshot's ORS section list (ADR-0033) and replaces the copy and its entries in one transaction, so a server that reads during the pull sees the old table or the new one.
- **Not there yet is not an error.** A 404 means the table is not published, and nothing changes, until it is.
- **A copy that was loaded is kept.** A table that answers 404 after it was loaded, a server that keeps failing, and a file that is not a table (not a PDF, no text layer, or no row of an ORS table in it) all leave the copy the index holds as it was. A file that parses to no entries is refused, not stored, because a table of no entries would say that no Measure changes the ORS. The build report's `statutes_affected_table` block says what each pull made of it: `loaded`, `unchanged`, `not_published`, `not_fetched` or `not_read`, whether the index holds a table after the pull (`held`), and for a `loaded` table the number of entries and the lines of its ORS table the parser could not read (0 for 2025R1's).
- **Kept like a document, not as one.** The copy has its `source_url` (the address the deployment named), the time the bytes it holds were retrieved (a later pull that finds the same bytes leaves it) and its content hash and text, in tables of its own (`statutes_affected_table`, `statutes_affected_entry`). It is not a Document of the glossary: it is in no search result, `get_document` does not serve it and the counts do not include it, because no feed row links it and the ticket asks for entries beside the links, not for another document to read. ADR-0002's mirror of what the feed links is untouched.

## Considered Options

- **Build the address from the Session key and one configured origin.** The path `/AutoPubs/artables2025R1.pdf` follows the Session key in the research, but a Legislative Counsel that moves the folder would need a code change; the whole address in one variable keeps the deployment in charge of it, as `OLIS_BASE_URL` is.
- **Treat any failure as "not published" and drop the copy.** A server that stops giving a file is not a reason to unsay what the Legislature published, and ADR-0005's removal rule asks for two complete pulls to miss a row; the table is one file, and the copy is kept whichever way the fetch fails.
- **Store the table as a Document of the Session.** It would be searchable and fetchable by id, but it would be 64 pages of rows in every search for a statute number and would change the counts and the tests of search that this ticket does not own.
- **Parse the table on every pull.** Parsing is cheap, but extracting 64 pages with PDF.js is not free on a two-core box shared with seven corpora (ADR-0007), and the file is unchanging for months.

## Consequences

- A database file built before this ticket lacks the two tables, and a server given it does not start (the reader prepares its queries when it opens the file); no database has been deployed (tickets #24 and #25), so the answer is to rebuild it, as ADR-0014 and ADR-0016 say for theirs.
- A parser that improves, or a new snapshot, reads the table again only after the copy is deleted or the file changes: the entries are read once for a file, as ADR-0015 reads a Version's links once.
- The retrieval time shown is the pull that first saw the bytes the index now holds, so an agent can tell a table retrieved after the Session ended from one retrieved before a correction.
