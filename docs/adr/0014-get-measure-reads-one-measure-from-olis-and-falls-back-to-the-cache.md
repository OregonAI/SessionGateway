# get_measure reads one Measure from OLIS when it is called, and the cache answers when that fails

ADR-0005 allows on-demand queries, and spec #1 (module 11) wants a Measure's status to be current, so `get_measure` returns a `live_status` block: the Measure's location, history, schedule and votes, read from OLIS when the call arrives and dated by the injected clock at the read. A read that fails does not fail the call: the cache answers, and the block says so. Ticket #21 built it; `0009-packages-and-a-split-database.md` records where the code sits.

- **Five requests, one for each kind of value, run together.** Each is `$filter=SessionKey eq '<key>' and MeasurePrefix eq '<prefix>' and MeasureNumber eq <number>`, with `$inlinecount=allpages` and the JSON `Accept` header, and no `/$count` request: a second count taken at another moment could disagree with the first on a feed that changes every five minutes, and one Measure's rows fit one page (`docs/research/olis-live.md` §1), so the first page's count checks the read.
  - `Measures`: `CurrentLocation` and `CurrentCommitteeCode`, the location. A Measure OLIS does not list is not an answer, so the lookup counts as failed.
  - `MeasureHistoryActions`: the history, in full, since the cached history is in full.
  - `MeasureVotes` and `CommitteeVotes`: the floor and committee votes. Each Legislator Code is resolved through the new `legislator_code` table (code to Legislator id), which the worker writes from the resolver, because the server has neither the alias file nor the resolver. A code the table does not hold, one OLIS's votes use for the first time, is shown as the code alone. Like the tables ticket #15 added, the table is made with `CREATE TABLE IF NOT EXISTS` by the worker's connection alone, which is the only one that runs the schema. A database file built before this ticket has no such table, and a server given it does not start: `openIndexReader` prepares the query that reads `legislator_code` when it opens the file, and `createSessionGatewayHandler` throws "no such table: legislator_code" at start-up, before any call. The worker creates the table when it next opens the file and fills it with its next full pull. No database has been deployed (tickets #24 and #25), so the answer is to rebuild it.
  - `CommitteeAgendaItems`, with `and MeetingDate ge datetime'<the time of the read, as Pacific wall-clock time>'`: the schedule, only the meetings still ahead. This is the first set read with the feed's misspelled `CommitteCode`, which the client hands on as `committeeCode`.
  The calls in flight stop on the first failure. A call for a Measure the index does not have, and a call the rate limit refuses, make no request, so a window's worth of calls makes at most five times the rate limit's requests (600 a minute with the default 120).
- **A failure is a value, and the cache answers.** An error status, a broken connection, no answer within `OLIS_LIVE_TIMEOUT_MS` (5 seconds, for all five requests together; the variable may be 1 to 30000 milliseconds, and the server refuses to start with another), a page the client cannot read, a read that counts more rows than it got, and a Measure OLIS does not list each make the block say `source: "cache"` and `lookup_failed: true`, hold the cache's location, history and votes, and name the reason in its `notice`. It is not an `isError` result (`src/CLAUDE.md`, "Errors"). The cache keeps no agenda items, so a block that fell back has `schedule: null`, which differs from `[]`, nothing ahead. The failure also goes to the deployment: `src/bin/server.ts` logs it as a JSON line.
- **The server is given what it needs, like the worker.** `OLIS_BASE_URL` (now required by the server, which refuses to start without it, because a deployment without it would answer every call from the cache), `OLIS_LIVE_TIMEOUT_MS`, `fetch`, a shutdown signal and a callback for failed lookups come in from `src/bin/server.ts`. The tool is now marked open-world.

## Considered Options

- **A failed lookup as an `isError` result.** The cache still answers (spec #1, story 44), so `src/CLAUDE.md` ("Errors") makes a fallback a normal result with a flag, not an error.
- **A `/$count` request beside each read, as the full pull makes.** A second request for each kind of value, taken at another moment than the rows.
- **A server that starts without an OLIS base URL.** It would answer every call from the cache and say the lookup failed, which looks like an outage of OLIS and is a missing variable.
