# Transcript passages are stored by the worker and shown by the tools only while the owner has published them

Spec #123 stage 2, decision 23: machine transcripts are built and ingested, and kept off the public deployment until the owner says "publish". Ticket #134 stores what the transcript read (ADR-0054) attaches, shows it in three tools, and puts the gate in the server. The decisions are where the files come from, how a passage is stored and found, how the gate is named and enforced, and where the notice goes.

## Decision

**Where the files come from.** A folder the deployment names, `TRANSCRIPTS_PATH`, holds the files `OregonAI/hearing-transcripts` writes, one for each recording, named `<eventId>.transcript.json`. The worker reads the folder at the end of every full pull and every increment, after the Recording Logs' turns are stored and cut, so that a log fetched in the pull has its transcript read in the same pull. Unset, the worker reads no folder, and the build report has no `transcripts` section (a report of a deployment without transcripts is as it was). The server never reads the folder.

**What the worker reads, and when.** For each Meeting, the Recording Logs that have an index are grouped by the event ID their links name; a file named for that event ID is read when it is not stored yet, or its sha256 changed, or what it was attached to changed. "What it was attached to" is a hash of the logs' ids, their turns, the logs' other entries and a version number (`ATTACHMENT_VERSION`) that is raised when the rules of attaching change, so a re-read index (new turns) and a change to the rules both attach the stored file again with no new file. A file whose sha256 and attachment are the stored ones is not read at all, so an unchanged transcript is never embedded again.
- The read is `readTranscript({ file, text, eventId, turns, entries })` with the turns of every log of the recording merged (the read orders them by second) and the entries of the logs' text. The worker keeps a log's text and turns and not its link annotations, so the entries come from `entriesOfLogText` (`recording-log`), which reads the text alone: an entry's second is its timecode (`offsetSource` "timecode"), where the turns' seconds are the links'. In the fixture the two are equal for every line (the link on a line gives its timecode in seconds); a log whose pages are read by timecode gives equal seconds by construction.
- A refused file (`unknown_version`, `event_id_mismatch`, `not_valid`) is named in the build report with the read's own message, and what the Meeting had stored before is kept. A file whose Meeting's log has an event ID and no speaker turn is refused `no_turns` by the worker: there is no player link of the log's own to build from, and nothing is guessed.
- The transcript read's drift is stored with the transcript (the median, the maximum, the number of turns over ten seconds, and whether the Meeting is flagged), and the build report lists every stored transcript that has a flag, whether or not this run read the file, so a flag does not disappear from the report at the next pull.
- Files of events no Meeting's log names are listed (`unmatched_files`); a folder the worker cannot list (it does not exist) is a `folder_error` in the report and does not fail the pull.

**How a passage is stored (schema step 4).** A transcript passage is not a slice of a document's text, so it is not a row of `passage`: it has its own table, `transcript_passage`, its own keyword entry (`transcript_passage_fts`, the passage's id as the rowid, the same tokenizer as `passage_fts`), and its vector in `passage_vector` under the hash of its text and the embedder's model id, like any passage (embedded like Testimony: real vectors in production, the fake embedder in tests, one vector for each distinct text). `transcript` holds a row for each (Meeting, event ID) with the file's name and sha256, what it was attached to, the audio's sha256 and duration, the model's id, when it was made and the drift. Step 4 adds two tables, an FTS table and indexes and alters no table that exists.
- One passage is one attached run of words (the read's passage: a segment, or the piece of one between two speaker changes), cut to the passage size (the embedder's `maxPassageTokens`) between words when it is longer. It is of a Recording Log (`document_id`): its turn's log, or for words that are no turn's the first log of the recording. It is linked to its turn by the turn's position in that log, or says it is a procedural entry (a motion, its result, a vote, a roll call: the entry's kind) or "speaker not given" with the reason (during a recess, after adjournment). It carries its start and end seconds and a Player link at its first whole second, built from the log's own link (`playerLinkOf` over a stored turn's link, which names the clientID and the event ID), never invented.
- The Agenda item and Measure of a passage are its turn's. For a passage that is no turn's they are the latest Agenda item line at or before its start, and the Measure it begins with when the index holds it (the same rule the turns follow).
- Storing a transcript replaces what the (Meeting, event ID) had, in one transaction with the vectors it lacked, and raises the search generation so the server loads the vectors again.
- The quality numbers of a segment (`avg_logprob`, `no_speech_prob`, ...) are not stored. ADR-0054 leaves what they mean for publishing to the gate; the gate below is the owner's one decision for the whole corpus, so nothing here judges them. A later ticket that wants them reads the files again, which are on disk.

**The gate.** `TRANSCRIPTS_PUBLISHED`, an environment variable the server reads once at start-up through the configuration module (`ServerConfig.transcriptsPublished`). Its value is the text `true` or `false`, and it is `false` when unset. Any other value (`yes`, `TRUE`, `1`) stops the start-up with a message that names the variable and never the value (`src/CLAUDE.md`, "Configuration"): a gate that guesses what "yes" means is a decision the owner did not make. The worker does not read it: it ingests regardless, so the owner publishes by changing the server's setting, with nothing to re-ingest. The gate is for the whole server, not for a Meeting or a tool. Turning it on is the owner's go-live decision for transcripts, recorded where deployment settings are recorded, and the box's database must have been upgraded to schema step 4 first (platform-deploy's schema gate holds the deploy until it is).

**What the gate keeps out.** With the gate off, no tool's answer holds any transcript text, and nothing is read from the transcript tables to build an answer:
- `search` queries no transcript keyword entry and loads no transcript vector (the vector cache never reads them), so a passage is found neither by its words nor by its meaning, and no hit has a `transcript`;
- `get_document` on a Recording Log reads no transcript, and the log's `speaker_turns` is exactly stage 1's: no `transcript` on the log or on any turn;
- `meetings` has no `has_transcript` field;
- `get_measure` never shows transcript text with the gate on either (its hearings name the first turn under an Agenda item, which is stage 1), so the gate changes nothing there.
Stage-1 turns are never gated and are unchanged either way. Each field the gate adds is optional in the tool's output schema and absent when the gate is off, so a result with the gate off is word for word what it was before this ticket.

**What the tools show with the gate on.**
- `search`: a transcript passage is a hit of its own (keyed by the log and the passage, as a turn is keyed by the log and its position). Its id and `document_id` are the log's, its `snippet` is the passage, and `transcript` says: `speaker` (the turn's speaker as logged, or "speaker not given"), `speaker_kind` (`turn`, `procedural`, `not_given`), `procedural` (the entry's kind, or `during_recess` / `after_adjournment`, or null), `turn` (the turn with its Legislator Code, Legislator, Meeting, Agenda item, Measure, timecode and Player link, or null), `meeting`, `agenda_item`, `measure_id`, `start_seconds`, `end_seconds`, `timecode` (the start as hh:mm:ss) and `player_link` at the start. The hit's `turn` stays null: that field means "this hit is a speaker turn of the log's own text", which a passage of spoken words is not.
- Ranking: the passages that hold every word are interleaved with the documents' by rank (reciprocal rank fusion, the sides' own fusion), because the two keyword indexes' BM25 scores are not comparable; the meaning side ranks transcript passages among the documents' by score, because one model made both vectors. A passage is subject to the call's filters as its log is (kind `recording_log`, committee, dates), except that its Measure is its own: a search of a Measure finds the words said under it, which the log itself (filed under a Meeting, not a Measure) never matched.
- `get_document` on a Recording Log with a stored transcript: each turn in `speaker_turns.turns` has `transcript`, the passages that fall in it in order (an empty list for a turn no words fall in), and `speaker_turns.transcript` has the model's id, when it was made, the passage count and `other_passages`, the passages that are in no turn (words before the first turn, during a motion, vote or roll call, in a recess, after adjournment), each saying why. A log with no transcript has none of these fields, though the gate is on.
- `meetings`: `has_transcript`, true or false for every meeting, while the gate is on.

**Where the notice goes: the envelope, decided for each result.** Every result that holds a transcript passage adds the sentence "This result includes a machine transcript of the official recording, not an official record." after the non-official notice. It is the envelope's, as the notice and its `source_url` clause are (ticket #98, ticket #120): a tool gives the envelope `carriesTranscript(answer)` from its own typed answer (a hit with a `transcript`, a log with a stored transcript's passages), and the envelope never scans a payload. The reasons it is not a field of each hit:
- #120's owner decision was that a notice is worded for each result, from what the result holds, so a result with no passage keeps the notice it always had, word for word (a seam-4 test in the envelope holds it);
- one sentence in the one place every tool's reader already looks cannot be left out by a tool that forgets it, which a field of a hit's object could;
- a result of `search` that holds a transcript hit and a document hit has one notice, and the sentence says "includes", so it is true of the result and is not read as a claim about every hit.
The sentence is added even when the result has no `source_url` clause. `search` with the gate off, `meetings` and `get_measure` never add it.

**The build report.** With `TRANSCRIPTS_PATH` set, a full pull's `build-report.json` has `transcripts`: `folder_error`, `stored` (the transcripts the index holds), `ingested` (the files read this time: Meeting, event ID, file, passages, how many were embedded and how many reused a vector), `refused` (file, reason, message), `drift_flags` (every stored transcript with a flag: Meeting, event ID, file, median, maximum, turns over ten seconds, whether the Meeting is flagged) and `unmatched_files`.

## Considered Options

- **Put a transcript passage in `passage`.** Rejected: a row of `passage` is a slice (`start_offset`, `end_offset`) of the document's text and its text is read from the document, and a passage of spoken words is no slice of the log. Rows of both kinds in one table would make every reader of `passage` (`passagesOf`, `replacePassages`, the vector load, the citation passage) tell them apart.
- **Store the log's entries, so the worker needs no re-reading of the text.** Rejected for now: a log stored before this step has none and would be fetched again for its links; reading the text alone gives the same entries, with timecode seconds, which the fixture shows equal to the links'. The ADR names the limit: an entry's second may differ from a link's on a log whose links cannot be matched, and then the pages are read by timecode for the turns too.
- **A gate for each Meeting, each tool, or a date.** Rejected: spec #123 decision 23 is one decision, "the owner says publish", and a finer gate is a second thing to get wrong on the public box.
- **Accept `1`, `yes`, `TRUE` for the gate.** Rejected: an unknown value fails the start-up instead (see above).
- **The worker reads the gate and ingests only when it is on.** Rejected by the spec: the transcripts are built and checked locally before the owner publishes, and publishing must be a change of the server's setting.
- **A `notice` on each hit.** Rejected: see "Where the notice goes".
- **Store the segment quality numbers and hide passages that are mostly silence.** Rejected here: ADR-0054 gives that to the publication decision, and a threshold chosen before the first real transcript has been read is a guess; the bake-off and the owner's reading of the first real files decide it.

## Consequences

- A deployment that sets `TRANSCRIPTS_PATH` needs schema step 4 first: the box's schema gate (`OregonAI/platform-deploy#45`) holds a deploy of this image with "needs a database upgrade" until the box's database is upgraded, which is expected.
- Going public is a change of one setting on the server and a restart. Going back is the same change; nothing is deleted or re-ingested either way.
- The seam-1 files for it are `test/tools/transcripts-published.test.ts`, `transcripts-unpublished.test.ts` and `transcripts-pull.test.ts`, over a made-up transcript labelled as one, timed to the real turns of the fixture's log 288741.
