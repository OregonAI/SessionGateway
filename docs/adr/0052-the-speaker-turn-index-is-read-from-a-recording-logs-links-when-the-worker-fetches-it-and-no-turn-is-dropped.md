# The speaker-turn index is read from a Recording Log's links when the worker fetches it, and no turn is dropped

Spec #123, stage 1, asks for every speaker turn of a committee hearing to be findable: who spoke, when, under which Agenda item, with a link into the Legislature's own player at that second. Ticket #125 wrote the parser (`parseRecordingLog`, pure); this ticket wires it to the worker, the store and two tools. The decisions are how a turn is stored, how it is linked, how a speaker becomes a Legislator, and what happens to a turn nobody can resolve.

## Decision

- **The worker reads a Recording Log's links when it fetches the file, and only then.** The store keeps a document's text and hashes, not its bytes (ADR-0005), and a PDF's link annotations are in the bytes. So `ingest` calls `extractPdfLinks` (`pdf-text`, `{page, url, rect}` for each link that points at an address) on the bytes it has just fetched, hands the text, the links and the Meeting's Agenda items to `parseRecordingLog`, and stores the result in the same pull as the document.
- **A log stored before this step is fetched once more, and the pull says what became of it.** A stored log with no index (`recordingLogsWithoutIndex`) is fetched again by the next pull that lists it, and only its index is stored: its text and search entry stay as they were. Each such fetch is counted in the build report's `recording_log_refetches.attempted`, and every log that is not read is named there, and as a `not_read` gap in `recording_log_gaps`, with its source URL:
  - *the fetch fails* (a status, a timeout, a file the extractor cannot read): the log goes in `recording_log_refetches.failed` with the reason. The log has no index, and the next pull tries it again;
  - *the bytes are not the stored file's*: the new bytes' SHA-256 is compared with the stored `content_hash`. When they differ, no turns are stored, because the turns would belong to bytes whose text the index does not hold. The log goes in `recording_log_refetches.bytes_changed` with both hashes, the stored text stays as it is, and the next pull fetches it again, so the report says it every pull until the file is the stored one or the owner decides what to do (the same rule as the nightly hash sample, ADR-0040: a replaced file is reported and never stored). The alternative of taking the new file's turns and keeping the old text was rejected: the turns' seconds and speakers would then not match the text `get_document` returns beside them.
  An increment does the same fetches and keeps the same store, but writes no build report: its logs without an index show in the next full pull's `recording_log_gaps`.
- **The index is two tables (schema step 2, ADR-0048).** `speaker_turn_index` has a row for each log with what reading it came to: `indexed` (the event ID, the pages read by timecode, the turn count, which `meetings` reads without reading the turns), `no_event_id`, or `conflicting_event_ids` (the IDs). `speaker_turn` has a row for each turn: the timecode, the second, where the second came from (`link` or `timecode`), the speaker as logged, the Legislator Code and Legislator id when the speaker resolves, the Agenda item text, its Measure id and the player link. The reader joins the Legislator's name from the Legislators it holds, as it does for votes, so a corrected name reaches every turn. Step 2 also runs `DROP VIEW IF EXISTS feed_row_state`, as the note beside the steps said the first step another ticket added should (nothing has read the view since ADR-0049). `versionOneSchema` is unchanged.
- **The Meeting's Agenda items and committee come from the store, not from the run's feed.** The documents step runs after the feed is stored, in a Full pull and in an Increment alike, and an Increment reads only the rows changed since the last run, so the feed in hand may lack the Meeting's other Agenda items and its members. `agendaItemsOfMeeting` and `committeeMembers` read what the store holds. The Legislators are read whole by both runs, so the resolver is the run's.
- **A speaker resolves to a Legislator Code by title, chamber, surname and first name, among the Meeting's committee and then among all the Session's Legislators (owner decision B, 2026-11-05).** `legislatorOfSpeaker(speaker, members, legislators)` is the rule, and it is exact:
  1. The line must begin with a title: "Chair", "Co-Chair", "Vice-Chair" (a committee office, any chamber's), "Rep." or "Representative" (a House member), "Sen." or "Senator" (a Senate member). A line with no title names no one: a witness who shares a member's last name is not that member. Titles that name both chambers name no one. The name is what follows the titles up to the first comma, read without accents or periods. A line that narrates an action after the name names no one either (ticket #141): when a word of the name, after its first, is one of "passes", "declares", "serves", "rescinds" or "moves" ("Co-Chair Gorsek passes the gavel to Co-Chair Smith", which before resolved to Rep. Smith G through its last word), the line is still a turn, kept with its text and no Legislator. The list is closed, so a narrating verb it lacks is read as before ("assumes", which the ticket named, is in no log and is not on it). Owner decision of 2026-11-05: a narrating line names no one; resolving it to its first-named person (usually the one speaking) was considered and declined.
  2. A candidate fits when the title's chamber is the chamber of its Legislator Code (the feed's codes begin "Rep" or "Sen"; an office title fits either), the name's last word is the last word of the candidate's name (the feed holds "Finger McDonald" as "McDonald"), and the logged first name or initial agrees. A line gives a first name when its name has more than one word and its first word is an initial or the start of the first name of some Legislator the resolver holds; "Hai Pham" and "B. Levy" give one and "Finger McDonald" does not, because "Finger" is the start of a compound surname. The logged word agrees when it is the start of the candidate's first name ("B" and "Bobby", "Greg" and "Gregory").
  3. The Meeting's committee members are looked at first (the alias file and the Legislators rows give their names, and a code that names no Legislator is no candidate). One fit resolves. Two or more fits resolve to no one, and the line is not looked up among the rest.
  4. When no committee member fits, the Session's Legislators (every code the resolver can resolve) are looked at with the same rules, and here a first name or initial must be given: a surname alone never resolves among everyone. One fit resolves; none or several leave the line as logged.
  Before this rule the one member whose last word matched resolved whatever the chamber or the first name: in the 2026R1 log `recording-log-2026r1-315399` (SCGG 2026-02-23), "Rep. Hai Pham, House District 36" resolved to Sen. Khanh Pham, a member of that Senate committee. The 2025R1 analogue is log 309305 (HREV 2025-06-11), where "Sen. David Brock Smith, SD01" resolved to Rep. Gregory Smith, a member of the House committee; it is now David Brock Smith, "Sen Smith DB". "Sen. Mark Meek, Senate District 20" testifying to SLB (log 302332, 2025R1) now resolves among the Session's Legislators to Mark Meek, "Sen Meek". A speaker no one resolves keeps the logged text, so an agent still sees it. The cost of the chamber rule is a log's own mistake: "Representative Broadman, Presiding Co-Chair" in the 2026R1 log 314057 names a Senator and no longer resolves (the next line, "Co-Chair Broadman", does).
- **No turn is dropped.** A turn is a line of the log the parser called a speaker, and each is stored with its text whatever the resolver says: `legislator_code` and `legislator` are null for anyone it does not resolve. A line in capitals ("REP. SCHARF DECLARES POTENTIAL CONFLICT OF INTEREST") is such a turn. The tool returns every turn, so an agent can see what was not resolved.
- **The player link is the log's own link with the turn's second.** `playerLinkOf` takes the first link that is a player link by the rule `eventIdsOf` uses (`/liz/mediaplayer`, with or without a trailing slash, and no looser path) and whose `eventID` is the log's event ID, and replaces only its `startStreamAt`, leaving every other byte of the link as the log has it (a link without one gets it at the end of its query). The address, `clientID` and `eventID` are the log's, never written by this service: `https://olis.oregonlegislature.gov/liz/mediaplayer?clientID=4879615486&eventID=2025011038&startStreamAt=4`. The 34 logs of the fixture all use that shape (`mediaplayer?`, no slash before the query, one `clientID`). For a turn whose second came from its link, the result is that link as the log prints it.
- **A turn's Measure is kept only when the index holds that Measure.** The Measure is the one the Agenda item's line begins with ("HB 2167 - Public Hearing"), minted as its id and checked against the Measures the store holds when the log is read (`heldMeasureIds`). A turn under an item that names a Measure the index does not hold (a bill outside a slice, or one the Session never had) has `measure_id` null and keeps the Agenda item's text, so an agent never follows an id to nothing. A log read before its Measure arrives keeps null until it is read again.
- **Agenda items are decided line by line, and the feed wins (owner decision A, 2026-11-05, amending Q5 of #125).** A log line is an Agenda item when it matches one of the feed's items for the Meeting (its measure id and action, or its text); otherwise the text heuristic decides that line. A line shaped like a person is never taken by the heuristic: "Name, Title" ("Betsy Imholt, Director, Department of Administrative Services"), or "Name - Organization" where the right side reads like an organisation or is "Self" ("Jane Doe - Self"). So a feed that holds only some of a Meeting's items (the fixture is a slice) no longer turns the other items' lines into speakers, and the turns after them carry the right item. The parser says how it found each (`foundBy`).
- **A log with no event ID, or with two, has no index and says so.** The text stays stored and searchable, the tools report the gap (`speaker_turns.gap`), and the build report lists the log (`recording_log_gaps`, with the IDs it names). The pages whose links could not be matched to their lines, whose turns are read from their timecodes, are in `recording_log_pages_read_by_timecode`. The parser's own decisions Q6 and Q7 of #125 stand, and Q5 is amended above.
- **The tools.** `get_document` on a Recording Log returns a `speaker_turns` field beside the text, which is as published (ADR-0002): `indexed`, `event_id`, `gap`, `conflicting_event_ids`, `turn_count`, `pages_read_by_timecode` and `turns` in media-clock order (the second, then the log's order), each with every field above. `meetings` gives each Recording Log a `speaker_turn_index` (`event_id` and `turn_count`, or null) and each Meeting `has_speaker_turn_index`. The result envelope is as it was.
- **Packages.** `pdf-text` gains `extractPdfLinks`. `recording-log` gains `legislatorOfSpeaker`, `measureOfAgendaItem` and `playerLinkOf`, still pure. `domain/speaker-turns.ts` holds the stored shapes. `database` stores and reads the index through `writer.ts` and `reader.ts`; `ingest/lib/speaker-turns.ts` is the one place that joins the parser, the store and the resolver; `mcp-server/lib/speaker-turns.ts` is the one place that shows a turn.

## Considered Options

- **Store the PDF bytes and read the links at serving time.** Rejected: the store holds no bytes, and the server reads the database and nothing else.
- **Read the links in a later step of the pull, like the Statute Links.** Rejected for a new fetch: the bytes are in hand only when the file is fetched. That is also why a log stored earlier is fetched once more.
- **Resolve a speaker by surname alone, among the committee's members or among everyone.** Rejected after the review of #126: it resolved a Representative to a Senator of the same surname. Chamber and first name decide, and among everyone a first name or initial is required.
- **Resolve a speaker only among the Meeting's committee.** Replaced by owner decision B: a Legislator who testifies to another committee is still a Legislator, and the committee is the first place to look, not the only one.
- **Build the player link from the Meeting's date or from the event ID alone.** Rejected: the `clientID` is the Legislature's, so it comes from the log.
- **Drop a turn whose speaker is a heading.** Rejected: the parser cannot tell a heading from a speaker without guessing, and a dropped turn is a gap nobody can see.
- **Take the new bytes' turns when a log is fetched again and the file changed.** Rejected: see "A log stored before this step".
- **Make each turn a Passage in this ticket.** Deferred to #127 (owner decision C, 2026-11-05): see "Turns and Passages".

## Turns and Passages

Turns are stored in their own table (`speaker_turn`) for structure: a turn has a second, a speaker, a Legislator, an Agenda item, a Measure and a player link, which a Passage has no place for, and `get_document` and `meetings` read them back whole and in media-clock order. They are not Passages in this ticket. Ticket #127 makes each turn a Keyword-only Passage of its Recording Log, linked to its turn, so that `search` finds a turn by its words through the existing keyword path and needs no second path for turns. The turn table stays the structure and the Passage is the way in; nothing here builds it. Ticket #127 did, in ADR-0053.

## Consequences

An agent reads a speaker's words' place in the recording and opens the Legislature's own player there; it does not read the words, which are in the audio (stage 2 of #123, ADR-0051).

The Agenda item and Measure of a turn are as good as the parser's two ways of finding an item, and a log that names an item neither the feed nor the wording shows (a heading written as a person) leaves the turns after it under the item before. A person-shaped line that is an Agenda item is not found by the text, and the feed finds it when it lists it.

The index does not hold the Measures a hearing names that it never held; the turn says so with a null Measure and the item's text.

Committee membership is the one the store holds at the pull, not the one on the day of the Meeting. A Legislator who changed chamber has a code for each chamber (the alias file joins them to one person), and a line is resolved by the code whose chamber the title names.

A log whose file OLIS replaces after it was stored is reported on every pull (`recording_log_refetches.bytes_changed`) and never read, until the file is the stored one or a later ticket decides how a replaced file is taken up.

Seam 1's expected values for the logs are in `test/tools/get-document-speaker-turns.test.ts` (each hand-counted from the log's lines, the links read from the raw PDF); the gaps, the page read by timecode, the Senate log with two Phams and the re-fetches that fail or find other bytes are made-up logs and the fixture's real log 288741, in `get-document-speaker-turns-pull.test.ts`, labelled so.
