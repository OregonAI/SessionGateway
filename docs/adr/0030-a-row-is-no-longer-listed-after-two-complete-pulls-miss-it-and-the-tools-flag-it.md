# A row is no longer listed when two complete full pulls in a row have not listed it, the state is two tables and a view, and the tools flag the row

ADR-0005 says that a full pull counts as complete only when every set's rows match its `$count`, and that a row absent from two complete pulls in a row is marked no longer listed: it leaves search results and stays fetchable by id. This is how that is built.

**A pull is complete or it is refused.** The OLIS client counts each whole entity set it reads with the `/$count` path segment and with the first page's `$inlinecount`, and hands the worker the two numbers it ends with: the rows the feed counted and the rows that came (`onSetRead`). The worker reads every set, and the pull is complete when no set is short. A pull with a short set stores nothing and throws, naming each short set with its two numbers, as it did before; the index goes on answering from the last complete pull (`get-measure-feed.test.ts`, "a pull that is refused"). It also writes `build-report.json` as `{ session, attempted_at, pull: { complete: false, entity_sets } }`, where each set has `counted`, `read` and `complete`, so that the operator reads which sets were short without reading the log. A refused pull replaces the last report, whose lists the next complete pull writes again. A complete pull's report has the same `pull` block with every set, and for each the rows the index lists and the rows it holds that are no longer listed. A refused pull is neither a pull that missed a row nor one that listed it: it is not a pull for the rule at all.

**The state is two tables and a view.** `feed_pull` has a row for each complete pull of a Session, numbered from 1 in the transaction that stores the pull's feed. `feed_row` has a row for every row the index keeps from the feed, by its entity set and its key, with the number of the latest complete pull that listed it and the document it links, if it links one. A row is listed while fewer than two complete pulls have missed it, which `feed_row_state` says (`last_listed_pull > latest - 2`); the same view gives the as-of time of the pull that last listed it. A complete pull writes only the rows it lists; a row it misses needs no write, so a row that is missing is not a row that is written. Only a complete full pull writes a number, and what ticket #17 inherits follows from that (below). The tools and search read the view, and nothing else keeps a copy of "listed". Search leaves out a document whose row is not listed in every query (keyword, citation, Versions of a Measure, the posting of an amendment) and in the load of the vectors; the worker raises the search generation when a pull makes a document no longer listed or lists it again, so a server that has held the vectors in memory reads them again even when two pulls share an as-of time.

**What is tracked, and by what key.** Every row of every set the worker reads: Measures (the Measure id), Legislators (the code), MeasureSponsors, MeasureHistoryActions, MeasureVotes and CommitteeVotes (the feed's id), Committees and CommitteeMeetings (their ids), CommitteeAgendaItems (the feed's id), the five sets that link a document (the document's id), CommitteeMembers, and ConveneTimes and LegislativeSessions (ADR-0042: a convening by its time and Chamber, the Session's row by its key; neither is shown by a tool). A meeting's agenda is the `AgendaUrl` of its CommitteeMeetings row and is tracked under that column's name, so a meeting that stays listed after OLIS stops linking its agenda leaves the agenda no longer listed. CommitteeMembers has a declared key (`CommitteeCode`, `CreatedDate`, `Title`) that is not unique (`docs/research/olis-odata.md` section 8, gotcha 5), so the worker reads the set and keeps every row by the whole row, every property the feed sent: Rep Helm and Rep Owens, Co-Chairs of HALNRW from one instant, are two rows. A row that OLIS changes is a new row, and the old one stops being listed. The code is stored as written. A code that names no Legislators row is counted against the source `CommitteeMembers` in the pull's unresolved codes and is not an error: a task force's members are not all Legislators ("Shanbo Zhang"). No tool shows the set yet; `build-report.json` lists, for each committee, the rows the table holds (their count, their Legislator Codes and the unresolved ones), which is how an operator sees that rows sharing a declared key were all kept and how `committee-members.test.ts` proves it.

**Nothing is deleted, and the tools do not hide.** Spec #1 and ADR-0005 say only that a row leaves search results and stays fetchable by id. `get_document` serves a document that is no longer listed with `no_longer_listed: true` and `last_listed_at`, the as-of time of the latest complete pull that listed it, and both are in every result (`false` and the index's as-of time for a document the latest pull lists). For a Proposed Amendment, whose node has a document for each posting, the amendment is listed while the feed lists any posting, whether or not a posting's file is stored: the state is read from the postings' feed rows (the ones `meeting_document` lists and the ones the store holds), so `get_document` and `meetings` agree about it. A citation of an item the index holds and the feed no longer lists (a Proposed Amendment whose postings are all unlisted, an ORS section that only unlisted documents name) is not an item the index lacks, so its note in `search` does not say so: it names the item's id, says `get_document` still serves it (for an ORS section, the documents that name it, with the count and the latest) and gives the time the feed last listed it (`test/tools/no-longer-listed-citations.test.ts`). A Measure the index holds has no such note: `get_measure` serves it and flags it. A row that is no longer listed and whose file this index never fetched, of any kind of document, is a tool error that says exactly that: it was listed and is not any more, the index never fetched its file, and no later pull will, because the feed no longer lists the row (a listed Testimony whose file is missing still gets the error that says the next pull fetches it; any other listed row whose file is missing is still an unknown id). The output schemas of `testimony` and `meetings` say the same of `fetched: false` on a flagged row (`test/tools/no-longer-listed-unfetched.test.ts` proves a fetched and a never fetched Exhibit and Proposed Amendment). The tools that list rows keep listing a row that is no longer listed, with `no_longer_listed: true` on the item, and leave the field out of every item the feed lists, so a list that nothing has left is the list it was: `testimony` (its `total` still counts the row; ADR-0031 records that this supersedes the reading of ADR-0017 that the row leaves once removals are marked), `meetings` (the meeting, its agenda, agenda items, Exhibits, Recording Logs and postings) and `get_measure` (the analysis documents, the Versions and postings in `statute_links_by_source`, and the Measure itself, with `last_listed_at`; `compare_amendment` shows the same postings, flagged the same way). A Measure that is no longer listed is still served by id. The rows `get_measure` shows that have no id of their own (history actions, votes, sponsors, the Statute Links themselves) are tracked and not flagged. Every flag, and the `get_document` and `get_measure` fields that carry the time, are written by `mcp-server/lib/listing.ts` and nowhere else.

## What ticket #17 inherits

Ticket #17 (the increments) adds writes that store rows between two complete pulls. The rule above holds for them if they keep to this, which is written down here because nothing in the tree can prove it until they exist.

- **An increment never changes the two-pull state of a row a complete pull has seen.** Each row has one number, the latest complete pull that listed it, and the upsert of a complete pull sets it. An increment that wrote the latest pull's number for a row that complete pull 6 missed would make pull 7's miss the first, and the row would stay listed after two complete pulls in a row missed it. So an increment writes nothing to `feed_row` for a row that is there.
- **A row first seen by an increment has no listing row.** The reader and search read a row with no listing row as listed, not yet checked by a complete pull (the state of an old file, above), so a stored document or Testimony an increment adds is searchable, shown without a flag, and served by `get_document` with `last_listed_at: null`, and nothing the tools do needs to change. The next complete pull that lists it gives it a number. An increment before the first complete pull has no number to write and needs none.
- **The cost is a row no complete pull ever lists.** A row an increment saw and OLIS deleted before the next complete pull has no listing row for a miss to age, so it stays listed. The same holds for the rows of an old file that the first complete pull does not read. The way to give such a row a clock is a number for the pull after which it was first seen, and that belongs to the ticket that sees the case in real data.
- **Every write that changes what search holds calls `bumpSearchGeneration`** (`database/writer.ts`), in its own transaction: the storing of a document's passages, the refiling of a document and a full pull's listing or unlisting of one. A write of passages that bypasses it leaves a server that has the vectors in memory with the old ones until the next pull moves the as-of time (`no-longer-listed.test.ts`, "leaves the meaning side, and returns to it, though the pulls share an as-of time").
- **Left to #17, because they need an increment to run:** the sequence in which complete pull 5 lists a row, complete pull 6 misses it, an increment sees it and complete pull 7 misses it, which must leave the row no longer listed; a row first seen by an increment, before and after the first complete pull, which must be searchable and unflagged; and an increment that stores passages, which must move the generation when the as-of time has not moved.

## Considered Options

- **A `missed` counter on each row, updated by every complete pull for every row it misses.** The same rule, but a pull writes a row for every absent row, and the counter and the increments of ticket #17 are two things to keep in step. The pull number a row was last listed in is one number, and its age is the difference.
- **A `listed` column on each table.** Every table and every query would carry it, and the vectors in memory would depend on it. One view over one table is one place to read.
- **Delete the row, or leave a no longer listed row out of every tool.** Spec #1 (story 47) says it stays fetchable by id, and a citation an agent gave yesterday would stop resolving. The tools that list rows are not search, and ADR-0005 does not say they hide a row: a withdrawn letter that vanishes from "who testified" is a loss an agent cannot see.
- **A flag in every item, true or false.** Each item of `meetings` would grow by a field, the 20,000-character page of a meeting would hold fewer meetings, and the tests that pin an item's fields would change for a field that is almost always false. The flag is present when true.

## Consequences

A database built before this ticket lacks `feed_pull`, `feed_row` and `committee_member`. The worker creates them, empty, when it opens the file (`CREATE TABLE IF NOT EXISTS`). A server opened on the old file before the worker has run does not start, the position of ADR-0014 and ADR-0016: no database has been deployed (tickets #24 and #25), so the answer is to rebuild it.

Once the worker has opened the file, a row it holds that has no listing row is read as listed, not yet checked by a complete pull. This is the rule of the reader and of search, and it holds for any row stored without a listing row: the rows of an old file, and the rows ticket #17 stores. Such a row is searchable and shown with no flag. `get_document` gives it `no_longer_listed: false` and `last_listed_at: null`, because no complete pull has listed it and the time is not known, and nothing throws for it. The first complete pull after the upgrade lists the rows it reads. A row it does not read, because OLIS stopped listing it before the upgrade, never gets a listing row, so it never ages: it stays listed. It is not hidden after one pull, which would break the two-pull rule, and it is not marked no longer listed, because no complete pull ever listed it to miss. A rebuild is how such a row is dropped (`test/tools/pre-listing-database.test.ts` shows both).

The analysis documents the feed lists for a Measure (`analysis_listing`, ADR-0013) are no longer replaced at every pull. ADR-0013 replaced them so that the count of the files the index does not hold yet would be what the last pull saw, and that makes one pull that misses a row change what `get_measure` shows, against ADR-0005's "one missing pull is not a withdrawal". The rows are kept, and `analysis_documents.not_held` counts the listed ones the store does not hold, reading each row's listing state like every other tool: one complete pull that misses a row changes nothing, and a row two complete pulls in a row have missed stops counting (`test/tools/no-longer-listed-unfetched.test.ts`, HB 3131: 2, then 2, then 1). This supersedes that sentence of ADR-0013's Consequences. Search now reads `feed_row_state` for every candidate document. On a synthetic Session of 132,000 documents and 1,056,000 passages (eight to a document, 1% of the documents last listed one pull ago; one thread, 20-core machine in use by other jobs, 2026-10-30) the load of the vectors took 3.8 to 4.6 s with no listing term and 4.4 to 5.4 s with it, about a seventh more, and the two forms of the term cost the same (`EXISTS ... listed = 1`, as first built, and `NOT EXISTS ... listed = 0`, which reads a row with no listing row as listed). An earlier run of this ticket reported no measurable cost (1.74 s against 1.72 s); a second run did not reproduce it, so it is not relied on. The server pays it when it loads the vectors, not on each search. Listing 330,000 rows in the transaction of a pull took 0.56 s for the first pull and 0.59 s for the second (the rows of a 2025R1 pull, counted from `docs/research/olis-odata.md` section 7, are about 282,000; one core, 2026-10-30).
