# The tools show only rows created by the clock, and the database readers hold the rule

Ticket #151. #83's first run of the 2026R1 questions against the full build found that a question asked at 2026-02-03 saw the Session as it stood on 2026-11-03: SB 1518-1 (posted 2026-02-02) sat on page 7 of 14 behind Enrolled Versions created in March, and a question passed only because a Version created the next day was visible. The builder pinned page numbers. The owner decided on 2026-11-05 that the tools leave out rows created after the server's clock instead.

## Decision

**A row created after the injected `Clock` is not there.** The tools never see it: not in a list, not in search, not by its id. In production the clock is now, so nothing changes except that a feed row stamped ahead of the server's clock is hidden until the clock reaches it. In an evaluation run the runner already moves the clock to each question's moment (`scripts/eval/runner.ts`), so a question sees the Session as it stood then.

**The rule lives in one place: the two database readers.** `openIndexReader(path, clock)` and `openSearchReader(path, clock)` open the server's connection through `openReadConnection(path, clock)`, which calls `showOnlyRowsCreatedBy` (`database/lib/created-before-clock.ts`). That installs, on the read-only connection only, a temp table of the documents created after the clock (see "Why it is fast") and a temp view over each table that holds a stamped row, with the table's own name (`measure`, `document`, `search_document`, `meeting_document`, `testimony`, `version_listing`, `analysis_listing`, `document_relation`, `speaker_turn_index`, `speaker_turn`, `speaker_turn_item_measure`). The readers' queries name those tables and so read the view; none repeats the rule, none can forget it, and no tool knows of it (seam 4: `database/tests/created-before-clock.test.ts`; seam 1: `test/tools/hide-future-rows.test.ts`). The worker's connection is another function and never installs the views, so the worker still sees and writes every row. The clock is read before each statement runs, so a clock that moves moves what is seen without reopening a reader.

Two things the views cannot do by themselves are done by the reader, in the same place:

- **An id the feed lists and no file is held for** (a row whose fetch failed, or Testimony) is answered by the Listing, which does not read the views. `findDocument` asks first whether the id is a document created after the clock (`temp.hidden_document`) and then answers as for an id the index has never heard of: `undefined`, which `get_document` words as "No document ...", with nothing of the row, its text, address or hash. A Proposed Amendment's id is unknown while every posting of it is later than the clock (its postings are `meeting_document` rows, which the view hides).
- **A relation that points at a hidden document is no relation** (`document_relation`'s view). An analysis document the feed places on a Version is on no Version while that Version does not exist yet (`placeAnalysis`: an edge to a document that is not there is worse than none), so it is listed as unmapped, with the reason the domain already gives.

**What a row's creation time is.**

- A Measure's own `created_at`.
- A document's: the `CreatedDate` of the feed row that links it, kept in `document_created` for every document the feed links (a Version, a Printed Amendment, a posting of a Proposed Amendment, an analysis, a Testimony, an Exhibit, a Recording Log, an agenda). A meeting's agenda is a column of its CommitteeMeetings row (`AgendaUrl`) and has no row of its own, so it takes the meeting row's `CreatedDate` (the client reads it from the row; the feed's CommitteeAgendaItems carry none). The OLIS client now reads `CreatedDate` from the CommitteeMeetingDocuments rows too (Exhibits and Recording Logs; before this ticket it read it from the other four sets only). There is no schema step: the table existed and the worker already writes it for every link that has a time. A database built before this ticket gets the Exhibits', Logs' and agendas' times at its next full pull, and until then those rows have none and are shown.
- What follows a document follows it: its passages and vectors (through `search_document`), its Statute Links and Agency Links (through the document), its Listing entries (`version_listing`, `analysis_listing`), its relations.
- **Speaker turns and transcripts follow their Recording Log's creation.** A turn, the turn index and the Agenda-item Measures of a log (`speaker_turn*`) are hidden with the log, and so are the passages of its turns (through `search_document`) and the hearings `get_measure` lists. A machine transcript (ticket #134, ADR-0055) is one Meeting's and is stored by the worker under the Recording Log's document id: each `transcript_passage` row has the log's `document_id`, and the passage is of that log and of its turn. It takes the log's creation time, and the same temp views hide it with the log: `transcript_passage` is hidden while its log is, so a hidden log's passages are found by no keyword search (their keyword entries are reached through the passage) and shown by no get_document; the `transcript` row (which has no log id, only the Meeting and the event ID the log's speaker-turn index names) is hidden while that log is, so `has_transcript` in meetings is false. The transcript vectors are read from the tables whatever the clock, like the documents', and each semantic search call leaves out the passages of a hidden log by the same hidden set. The publication gate is a separate rule and unchanged: with it off, no transcript is loaded or shown at any clock. No schema step.

**Time zones.** The feed's `CreatedDate` has no offset. It is Pacific wall-clock time, which `docs/research/olis-odata.md` had as inferred, and which is now measured: the hour of day of the `CreatedDate` of 288,341 rows in the 2025R1 cache (`.cache/olis-2025R1/feed/`, measured 2026-11-05) peaks at 11:00 and 12:00 (43,340 and 44,308 rows), holds 23,913 to 24,792 an hour from 14:00 to 16:00, falls to 3,184 to 5,344 an hour from 19:00 to 23:00 and is lowest from 01:00 to 04:00 (315 to 481); if the text were UTC the working day would peak at 19:00 and 20:00 Pacific. The OLIS client reads the text as Pacific and writes it with the offset in force that day (`atPacificLocalTime`), so a stored created time names an instant. The comparison is of instants, never of text: SQLite's `unixepoch(created_at, 'subsec')` against the clock's epoch seconds. So a row created at 16:42 Pacific on 2025-02-03, which is 2025-02-04 00:42 UTC, is shown to a clock of 16:50 Pacific that day, and a row at 01:30 PDT is before the clock's 01:15 PST on the day the hour repeats, which comparing the text would get wrong. A time that is the same instant as the clock is shown ("created at or before the clock"). The resolution is the millisecond (SQLite rounds a seven-decimal feed time to it, and the clock is in milliseconds), so a row can show 0.4 ms early, which no clock the tools see tells apart. There is no allowance for the feed's clock running ahead of the server's: a row OLIS stamped a few seconds ahead appears when the server's clock reaches it.

**A row with no creation time is shown.** The feed gives a few sets no `CreatedDate` (FloorLetters), a link's `CreatedDate` may be null (`nullish` in every row schema), and a database built before the Exhibits' and Logs' times were read has none. Nothing says such a row is from after the clock, and hiding it would hide it for ever, from production as well as from a question; a time SQLite cannot read gives NULL, which is not "after" either. The cost is that an evaluation run sees a row of that kind whatever its moment.

**Rows the rule does not reach, and why.** No creation time is stored for them (the tables keep the feed's `ActionDate`, `MeetingDate` or `LetterDate`, which are the times things happened, not the time the row was created), and storing it is a schema step (ADR-0048), which this ticket does not take:

- sponsors, history actions, floor votes and committee votes (the ticket names them), Floor Letters, meetings, agenda items, committees and committee members. **Owner decision C (2026-11-05): this is a follow-up, ticket #153** (a schema step for their creation times); this ticket does not hide them.

A history action's own date is not used in their place: OLIS may carry an action dated ahead of the row's creation, and a production reader must change nothing but the guard above. Until the times are stored, a question's `get_measure` shows a Measure's sponsors, history and votes as of the last pull, whatever its moment. Ticket #153 stores `CreatedDate` for these rows (a schema step and a full pull to fill it) and hides them.

**The search's meaning side is filtered at every call (owner decision A, 2026-11-05).** The vectors are loaded for the index's generation and as-of time, as before (`createVectorCache`), but of every document, whatever the clock (`vectors()` reads `main.search_document`). Each call then leaves out the hidden documents: `SearchIndexReader.hiddenDocuments()` answers the same cached set the views use, and `embeddingCandidates` drops a hit whose document is in it before it asks for details. So a handler asked at a late clock and then at an early one gives no hidden hit, and no error names a hidden id (the first version of this ticket loaded the vectors through the view, so a clock moved back left a hidden document in them, and `details` threw "The index has no document ..." with its id). A clock moved forward needs no new load either: the document is in the vectors already.

**The Statutes Affected Table shows the entries of the Versions the clock has reached (owner decision B, 2026-11-05).** The table is one file read at the last pull, and it lists entries for Versions that did not exist at an earlier clock. `statutesAffectedTableOf` leaves out an entry whose level names a Version the feed lists for the Measure and the clock has not reached (`hidden_version_listing`: a listed Version whose document is hidden, and no visible Version of the same description), as if the table had been read that day. An entry that ends in an E alone (`loneE`) and one whose level names no single Version (a conference report's "BCC") are kept: the table does not say which Version they mean, and nothing is guessed. When every entry of a Measure is left out the table lists nothing for it (`lists_measure` false), as for a Measure it never listed.

## Why it is fast

The first version filtered with `NOT IN (SELECT document_id FROM document_created WHERE unixepoch(created_at, 'subsec') > created_clock())` in each view, which SQLite rebuilt for every statement by reading all of `document_created` and calling `unixepoch` per row: on the 2026R1 index (36k rows) `search` went from 8 to 102 ms and `get_measure` from 8 to 107 ms (25 to 120 and 10 to 148 ms with the real embedder). Now:

- `temp.document_epoch` holds each stamped document's creation as epoch seconds, with an index. It is made again only when another connection has committed (`PRAGMA data_version` moved), so `unixepoch` runs once for each row for each change to the index, not once for each statement.
- `temp.hidden_document` holds the ids created after the clock, read from that index range, and is refreshed only when the clock's value differs from the one it was taken at. A view probes it by primary key. In production it is empty or nearly so.
- The connection's `prepare` is wrapped so that a statement's `run`, `get`, `all` and `iterate` refresh first. No reader has to remember to, and the rule stays in `created-before-clock.ts`.
- `created_clock()` (used by the Measure view, which has few rows) answers the clock value of the last refresh. It is registered as deterministic because it takes no argument and its value changes only between statements, never during one, so SQLite reusing one evaluation for a statement is what is wanted: one instant for the whole statement.

Measured on a copy of the 2026R1 index at a clock of now (medians of 15 calls, 3 runs; the embedder a stub, so the scan of the vectors is included and the embedding is not): main 7.7 / 7.7 ms, the first version 101.9 / 106.7 ms, now 8.4 / 8.1 ms (`search` / `get_measure`). At a clock of 2026-02-03, where many documents are hidden, the first version took 438 / 169 ms and this one 8.3 / 6.7 ms.

## Consequences

- `openIndexReader` and `openSearchReader` take a `Clock`, and so does `openReadConnection`. The entry scripts pass the one clock they already create; the evaluation runner reads the database's Session and as-of time with the system clock, which hides nothing it reads (those tables are not stamped). The seam-4 arrangements of the made-up index use a clock after January 2099, which hides nothing, so their stories are unchanged.
- A question's moment must be after the creation of every row it reads. #83's e-analysis asks about HB 4060's analysis documents on the A-Engrossed Version at 2026-02-26, and that Version was created 2026-02-27 16:51 (the analyses, 95184 and 95187, on 2026-02-25), so at its moment they are on no Version: its moment moves to 2026-02-27 afternoon or later.
- `get_measure`'s `created_at` of a Measure created after the clock is not shown: the Measure is unknown.
- `counts` (`session_overview`) counts what the clock shows.
- The cost is one primary-key probe for each row a query reads through a view, an empty `NOT IN` list in production, and a `PRAGMA data_version` read before each statement (see "Why it is fast"). While a pull commits, the next statement after each commit makes `temp.document_epoch` again, a read of `document_created`, once for each call that follows a commit.
- `get_measure`'s Statutes Affected Table follows the clock (decision B), the search's meaning side follows it at each call (decision A), and the ids of hidden documents are named by no error.
