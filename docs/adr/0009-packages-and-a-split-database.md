# Packages for the tracer bullet and the tickets after it, with the database's writer and reader as two entry points

Spec #1 lists twelve modules, and `src/CLAUDE.md` asks the ticket that first builds any of them to record how they become packages. Ticket #4 builds the path from OLIS to `get_measure`, so seven packages exist after it (`src/packages/`); each later ticket that adds a package or an entry point adds its row to the table below, as ticket #8 did with `legislators`, ticket #15 with `domain/votes.ts`, ticket #21 with `domain/schedule.ts`, ticket #5 with `pdf-text` and `domain/documents.ts`, ticket #10 with `oregonai-snapshot` and `domain/oregonai.ts`, ticket #12 with `domain/analysis.ts`, ticket #6 with `statute-links` and `domain/statute-links.ts`, ticket #7 with `agency-links` and ticket #13 with `readAmendedVersionHeader` and the reader and writer methods for Statute Links, and the sections after the table say what that ticket changed. Each package's root files are its entry points; everything below them is hidden (`src/packages/README.md`). The `example/` template stays until the owner deletes it.

| Package | Entry points | What it is |
|---|---|---|
| `time` | `clock.ts`, `pacific.ts` | The injected `Clock` and the system clock; the Pacific `Timestamp`: an instant or a Pacific wall-clock reading written with the offset in force. It knows the zone and no source's text format. |
| `domain` | `index.ts`, `legislators.ts`, `votes.ts`, `schedule.ts`, `documents.ts`, `oregonai.ts`, `analysis.ts`, `statute-links.ts` | The glossary's words as types (`SessionKey`, `Measure`, `MeasureId`, `MeasureLocation`, `HistoryAction`; `Legislator`, `LegislatorId`, `Sponsor` in `legislators.ts`; `FloorVote`, `CommitteeVote`, `LegislatorVote` and the entries the feed records them as, and the grouping of entries into votes, in `votes.ts`; a Measure's scheduled `AgendaItem` in `schedule.ts`; documents, committees, meetings and their ids in `documents.ts`; the ids of Agencies (`AgencyId`, the registry slug) and of ORS sections and chapters (`ors-163a.040`, `ors-chapter-657b`), and `SnapshotVersion`, in `oregonai.ts`; the reading of an analysis document's Version label in `analysis.ts`; the Statute Link type in `statute-links.ts`) and the one place that mints and parses ids and builds the OLIS page URL. |
| `statute-links` | `index.ts` | Spec module 4, the Statute Link parser (ticket #6): `parseStatuteLinks`, text in and links out, with the ORS section list as a parameter. It does no I/O and knows no database, no MCP and no feed. |
| `config` | `index.ts` | The environment read once through zod, for the worker and for the server. |
| `legislators` | `resolver.ts`, `aliases.ts` | Spec module 7 (ticket #8): resolves a Legislator Code to a Legislator through the feed's Legislators rows, then the hand-kept alias file (`data/legislator-aliases.json`, read by `aliases.ts`), and tallies the codes it could not resolve for the ingest worker's report. It builds on `domain` and sits below `ingest`. |
| `pdf-text` | `index.ts` | Part of spec module 3 (ticket #5): the only code that reads PDF bytes, with unpdf (ADR-0010). |
| `oregonai-snapshot` | `index.ts` | Spec module 6 (ticket #10): parses the OregonAI snapshot file at the edge. Only the ingest worker imports it (ADR-0012). |
| `olis-client` | `index.ts` | Spec module 1: the only code that sees the feed's own shapes, among them the offset-less timestamps, which it reads as Pacific local time and refuses in any other form. |
| `database` | `writer.ts`, `reader.ts` | The only code that imports `node:sqlite`. |
| `agency-links` | `index.ts` | Spec module 5, the Agency Link extractor (ticket #7): pure functions from a Fiscal Impact Statement's text, Version or Proposed Amendment text, or a Testimony row's `Organization` to Agency Links with their evidence. The agency registry is a parameter. It imports only `domain`, for the Agency id (`AgencyId`, minted in `domain/oregonai.ts`). The ingest worker imports it for Testimony (`testimonyAgencyLinks`, ticket #14, with the build-time snapshot's registry); the other extractors wait for #16. |
| `ingest` | `index.ts` | Spec module 2, the full pull only. |
| `mcp-server` | `handler.ts`, `http.ts` | The tool contract and its rate limit (one ceiling over every caller, timed by the injected `Clock`), the live lookup of `get_measure` (ticket #21, ADR-0014) with its cache fallback, and serving it on a port behind the Host and Origin guards. |

Dependencies point one way. `time` is at the bottom, `domain` is on it, `config`, `legislators`, `statute-links`, `agency-links`, `pdf-text`, `oregonai-snapshot`, `olis-client` and `database` build on those (`legislators`, `statute-links` and `agency-links` on `domain` alone, `pdf-text` on neither), and `ingest` and `mcp-server` sit on top. `src/bin/ingest.ts` and `src/bin/server.ts` are the two entry scripts: each loads its configuration and creates what it needs (the clock, `fetch`, the shutdown signal, and for the server its pino logger) once, and passes it down.

**What the OLIS client reads so far.** Ticket #4 reads one entity set, Measures. Of the feed's quirks (`src/CLAUDE.md`, "Shape"; `docs/research/olis-odata.md` sections 1 and 8) the client therefore handles, and the tests show, `$inlinecount`, paging with a relative `odata.nextLink`, `/$count` without a JSON `Accept` header, and timestamps with no offset. Decimal keys serialized as strings and misspelled property names do not occur in Measures: they are in sets the client does not read yet (`MeasureSponsors`: `MeasureSponsorId` and `LegislatoreCode`; `MeasureAnalysisDocuments`: `MeasureAnalysisId` and `CommittteCode`; `CommitteeAgendaItems`: `CommitteCode`). The first ticket that reads one of them handles the quirk in `olis-client/lib/`, exposes the corrected name or number as a domain type, and shows it through a tool. Reading a set only to exercise a quirk, with nothing an agent could see, would have meant a test below the tools, which `test/CLAUDE.md` does not agree as a seam.

**Ticket #8 reads two more sets.** The client now reads `Legislators` and `MeasureSponsors`, and handles the quirks the paragraph above says were waiting for them: `LegislatoreCode` is read under its misspelled name and handed on as `legislatorCode`, and `MeasureSponsorId` and `PrintOrder` arrive as strings and leave as numbers. `get_measure` shows the sponsors through the tool, which is where the test sees the quirks. The sponsors are stored in `legislator` and `sponsor` tables in the same transaction as the Measures, resolved by the worker, so the server needs neither the alias file nor the resolver. The `sponsor` table keeps every MeasureSponsors row with its kind, so the Committee and Presession rows, which name no Legislator, are not lost: `get_measure` shows them as `committee_sponsors` and `presession_messages`. The reader puts the Member rows in print order with `comparePrintOrder` (`domain/legislators.ts`), since that order depends on the Measure's own chamber and on names, which no column of the feed holds. The alias file is `legislators/data/legislator-aliases.json`; `src/bin/ingest.ts` passes its path (`committedAliasFilePath`, exported by `aliases.ts`) to `readLegislatorAliases`, so a seam-1 test gives the worker another file through `startSystem`.

**Ticket #15 reads four more things.** The client now reads the location fields of Measures (`CurrentLocation`, `CurrentCommitteeCode`) and three more sets, `MeasureHistoryActions`, `MeasureVotes` and `CommitteeVotes`, and `get_measure` shows them as `location`, `history`, `floor_votes` and `committee_votes`, as of the last full pull; the live status block is ticket #21's. None of the quirks that paragraph above kept for later is in them: no decimal key is sent as a string and no property is misspelled (`docs/research/olis-votes.md` §1 has the cache's types for every property of the four). What they do have, and what the client handles and the tests show through the tool:
- Timestamps with no offset: `ActionDate` (history and floor votes) and `MeetingDate` (committee votes) are read as Pacific local time through the same `feedTimestamp` as `CreatedDate`, and refused with an offset. `get_measure` shows each with the offset in force that day.
- Property names that say something else: the Legislator Code of a vote is in `VoteName`, and the vote itself is in `Vote` in `MeasureVotes` but in `Meaning` in `CommitteeVotes`. The client hands on `legislatorCode` and `vote` for both.
- The chamber is a letter ("H", "S"); the client hands on `house` or `senate` and refuses any other letter.
- One row for each Legislator in each vote: the client hands on one entry for each row, and the reader groups them, a floor vote by `MeasureHistoryId` and a committee vote by `CommitteeReportId`. The feed gives some committee rolls twice, as two reports of the same rows (`docs/research/olis-votes.md` §3), so the reader lists a roll once when a later report of the same committee and meeting holds the same Legislator Codes with the same votes. It keeps two rolls that differ as two votes, so no row of the feed is dropped.

The worker resolves the Legislator Code of every vote entry through the resolver, counted against the sources `MeasureVotes` and `CommitteeVotes` in the build report, and stores the entry with the Legislator's id in `floor_vote` and `committee_vote`, in the same transaction as everything else. The `history_action` table and the two columns that the `measure` table gained (`location`, `committee_code`) are written there too. The vote word is kept as the feed's string, since nothing branches on it and a closed set would stop a pull on the first new word. Committee codes are shown as codes: committee names wait for the ticket that reads `Committees`. The tables were created with `CREATE TABLE IF NOT EXISTS`, so a database file built by an earlier version has no `location` column on `measure` and the worker's pull fails with SQLite's "table measure has no column named location" (`docs/research/olis-votes.md` §7); no database has been deployed (tickets #24 and #25), so the answer is to rebuild it, and a migration waits for the first release that needs one.

**Ticket #21 adds an entry point and a client method for the live lookup.** What `get_measure` reads from OLIS when it is called, what a failed read is, and what the server needs in order to read it are ADR-0014's decision; this ADR records only where the code sits.
- `domain/schedule.ts` is a new entry point of `domain`: `AgendaItem` and its order.
- The OLIS client gains one method on its existing entry point, `readMeasureLive(key, readAt, signal)`, so the only code that sees the feed's shapes is still the code that reads them, live or in a pull. The feed's misspelled `CommitteCode` is read in `olis-client/lib/agenda-items.ts` and handed on as `committeeCode`.
- `mcp-server/lib/live-status.ts` calls it and decides what a failure is. It groups the vote entries with the same functions the reader uses: `groupFloorVotes` and `groupCommitteeVotes` (with the repeated-roll rule) moved to `domain/votes.ts` for that.
- The worker writes a `legislator_code` table (code to Legislator id) beside the other tables, from the resolver, because the server has neither the alias file nor the resolver.
- `src/bin/server.ts` creates and passes down what the lookup needs, as `src/bin/ingest.ts` does for the worker: `fetch`, the shutdown signal, the OLIS base URL and the bound on a lookup, with a callback that logs a lookup that failed.

**Extended by ticket #5, the document store.** Spec module 3 is not a package of its own: its fetching is `ingest`, its reading of the feed `olis-client`, its text `pdf-text`, and its storage `database`.
- A ninth package, `pdf-text` (`index.ts`), is the only code that reads PDF bytes (ADR-0010).
- `domain` gains a fifth entry point, `documents.ts`: document kinds, the ids of documents, committees and meetings, and the types the store and the server share. The entry points before it stay as they were.
- `olis-client` reads the document-bearing sets (`MeasureDocuments`, `MeasureAnalysisDocuments`, `CommitteeProposedAmendments`, `CommitteeMeetingDocuments`, `CommitteePublicTestimonies`, `Committees`, `CommitteeMeetings`) and fetches documents, retrying transient failures. The quirks that "What the OLIS client reads so far" says no set of #4 shows, and that tickets #8 and #21 have not met, are now in `lib/documents.ts` and `lib/meetings.ts`: `MeasureAnalysisDocuments` brings the misspelled `CommittteCode` and the string key `MeasureAnalysisId`, and a `CommitteeProposedAmendments` row can write an amendment number with a trailing space. They reach an agent through `get_document`.
- `database` gains the document, relation, committee and meeting tables, behind `writer.ts` and `reader.ts` as before.
- `mcp-server` registers `get_document` and `session_overview`.
- `OLIS_DOCUMENT_ORIGIN` (optional, `https://olis.oregonlegislature.gov` by default) is where the worker fetches documents from, because they are not on the feed's host. Only a test sets it.
- ADR-0011 records the shape of the documents themselves.

**Extended by ticket #10, the OregonAI snapshot (ADR-0012).**
- A tenth package, `oregonai-snapshot` (`index.ts`), parses the snapshot file at the edge: `parseSnapshot` and `loadSnapshot`, and the types `Snapshot` and `Agency`. Only the ingest worker imports it; a `dependency-cruiser` rule keeps the server from reaching it.
- `domain` gains a sixth entry point, `oregonai.ts`: the ids of Agencies and of ORS sections and chapters, and `SnapshotVersion`. The entry points before it stay as they were.
- `database` records the version of the snapshot with the full pull (`snapshot_state`, written in the same transaction as the as-of time) and `reader.ts` reads it back.
- `config` adds `SNAPSHOT_PATH` to the worker's configuration, and `mcp-server`'s `session_overview` reports the version.
- Four more layering rules in `.dependency-cruiser.cjs` keep OregonAI out of the server path: the server never reaches `oregonai-snapshot`, nothing under `src/` imports `scripts/`, nothing under `src/` imports a `devDependencies` package, and the server path imports no built-in that opens a connection. Three ESLint rules close the rest (the global `fetch`, `node:http` beyond `createServer`); ADR-0012 has them.

**Extended by ticket #12, analysis documents in `get_measure`.** No package is added.
- `domain` gains a seventh entry point, `analysis.ts`: the one reading of the feed's `Version` label and `IsMinority` flag on an analysis document (`placeAnalysis`), which the OLIS client uses to write the Version an analysis points at and `mcp-server` uses to group a Measure's analysis documents (ADR-0013).
- `Measure` gains `digest` (the feed's `MeasureSummary`), `DocumentLink` gains an optional `versionLabel` and `isMinority`, and `database` stores them (`measure.digest`, `document.analysis_version_label`, `document.analysis_is_minority`) and answers `analysisDocuments(measure)` through `reader.ts`. `writer.ts` records the analysis documents the feed lists for each Measure before it fetches any file (`FullPullRecord.documentLinks`, table `analysis_listing`), and `reader.ts` counts the ones the store does not hold (`analysisNotHeld`).
- `mcp-server` adds `digest` and `analysis_documents` (by Version, the unmapped ones, and `not_held`) to `get_measure`'s output (`lib/analysis.ts`).

**Extended by ticket #6, the Statute Link parser.**
- An eleventh package, `statute-links` (`index.ts`), is spec module 4 and test seam 2: `parseStatuteLinks` reads a Version's or Proposed Amendment's text into Statute Links and relating-clause edits, expanding ranges against the ORS section list it is given.
- `domain` gains an eighth entry point, `statute-links.ts`: the Statute Link and its target. The ORS ids a link points at are minted and parsed in `oregonai.ts`, which ticket #10 also wrote them in: when the two tickets met, the ids were kept in that one module (`src/CLAUDE.md`, "Shape"), with #6's shape of a chapter and a section (one to three digits and a letter; three or four digits), which every statute id of the ERF checkout the snapshot came from has.

**Extended by ticket #7, the Agency Link extractor.**
- A twelfth package, `agency-links` (`index.ts`), is spec module 5 and test seam 2: Fiscal Impact Statement units, names in the text and Testimony organizations in, Agency Links with their evidence out, with the agency registry as a parameter.
- It adds no entry point to `domain`. Ticket #7 minted the Agency id in a `domain/agencies.ts` of its own (`AgencyId`) while ticket #10 minted the same registry slug in `oregonai.ts` (as `AgencySlug`); when the two tickets met, the one type became `AgencyId` in `oregonai.ts`, named like every other id, and `agencies.ts` was removed.

**Extended by ticket #13, `compare_amendment` and the Statute Links of `get_measure` (ADR-0015).** No package is added.
- `statute-links` gains one function on its existing entry point, `readAmendedVersionHeader`: the Version and the Measure a Proposed Amendment's header names. It is pure, like `parseStatuteLinks`, and has a seam-2 table of its own.
- `domain` gains no entry point. `documents.ts` mints the reference to an amendment (`parseAmendmentReference`, from a citation or an id), parses an amendment number and mints its id from that parse (`parseAmendmentNumber`, `amendmentIdOf`, with a seam-2 table in `domain/tests/`), names a Version from a letter (`versionDescriptionOfLetter`) and places the amendment on a Version (`placeAmendment`, `versionRankOf`); `statute-links.ts` holds the four link kinds (`statuteLinkKinds`), the relating clause edit (moved there from the parser, which re-exports it, so the database and the server can name it without importing the parser) and the shapes of what was read of a file.
- `database` stores what the worker read (`statute_parse`, `statute_link`) through `writer.ts` (`unreadStatuteFiles`, `storedText`, `storeStatuteParse`) and answers `findAmendment`, `findMeasureAmendments` and `findMeasureVersions` through `reader.ts`.
- `ingest` reads the stored Versions and postings at the end of a full pull, after its files are stored.
- `mcp-server` registers `compare_amendment` and adds `statute_links_by_source` to `get_measure`; `lib/statute-links.ts` is the one place that decides how a link is shown.

**The database is two entry points, not one.** The worker writes and the server reads (ADR-0007), and the SQLite connection modes differ: `writer.ts` opens with WAL and `timeout: 5000`, `reader.ts` opens `readOnly` with `timeout: 5000`. Giving each side its own entry point lets the boundary check say that the server's code and entry script may import `reader.ts` and never `writer.ts`, and that the worker may import `writer.ts` and never `reader.ts` (the `server-reads-only` and `worker-writes-only` rules in `.dependency-cruiser.cjs`). A server that cannot reach the writer cannot write by mistake. Later tickets add queries to `reader.ts` and `writer.ts` (or further entry points beside them, such as a search index) rather than a second way into SQLite.

**Time and ids are packages of their own.** The worker dates a pull and the client dates every row, and what the server shows has to agree with both; the configuration, the client, the database and the server all use the same ids. So each lives once, in a package at the bottom. Pacific time uses Node 26's native `Temporal`, not the process time zone, which is why the tests run under a zone other than Pacific. How the feed writes a timestamp (no offset, read as Pacific) is a feed shape, so `src/CLAUDE.md` keeps it in the OLIS client: `time` turns a Pacific wall-clock reading into a `Timestamp` and the client's `lib/timestamps.ts` is the only code that reads the feed's text.

Later tickets add packages as their modules arrive (the document store, the Statute Link parser, the Agency Link extractor, the embedder, search) and add entry points to these. A new MCP tool is a file in `mcp-server/lib/` registered in `handler.ts`.

## Considered Options

- **One package per spec module, all twelve now.** Most would be empty folders, and their interfaces would be guesses before any caller exists.
- **One `core` package.** Nothing would be hidden, and the read-only server could reach the writer.
- **Separate packages for the writer and the reader.** They share one schema and one connection module, so splitting them would duplicate the schema or expose it.
- **A types-only package beside `domain`.** Minting an id needs the types it returns, so the two stay together.
