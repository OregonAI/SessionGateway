# Packages for the tracer bullet and the tickets after it, with the database's writer and reader as two entry points

Spec #1 lists twelve modules, and `src/CLAUDE.md` asks the ticket that first builds any of them to record how they become packages. Ticket #4 builds the path from OLIS to `get_measure`, so seven packages exist after it (`src/packages/`); each later ticket that adds a package or an entry point adds its row to the table below, as ticket #8 did with `legislators`, ticket #15 with `domain/votes.ts`, ticket #21 with `domain/schedule.ts`, ticket #5 with `pdf-text` and `domain/documents.ts`, ticket #10 with `oregonai-snapshot` and `domain/oregonai.ts`, ticket #12 with `domain/analysis.ts`, ticket #6 with `statute-links` and `domain/statute-links.ts`, ticket #7 with `agency-links`, ticket #13 with `readAmendedVersionHeader` and the reader and writer methods for Statute Links, and ticket #9 with `embedder`, `search`, `domain/search.ts`, `domain/citations.ts` and `database/search.ts`, ticket #16 with `domain/agency-links.ts`, ticket #95 with `database/checkpoint.ts`, ticket #98 with `mcp-server/envelope.ts`, ticket #96 with `ingest/snapshot-read.ts`, ticket #99 with `statute-links/measure.ts` and `statute-links/table.ts`, ticket #125 with `recording-log`, ticket #100 with a change to the entry points `olis-client/index.ts` and `database/writer.ts`, and the sections after the table say what that ticket changed. Each package's root files are its entry points; everything below them is hidden (`src/packages/README.md`). The `example/` template stays until the owner deletes it.

Dependencies point one way. `time` is at the bottom, `domain` is on it, `config`, `legislators`, `statute-links`, `agency-links`, `recording-log`, `pdf-text`, `oregonai-snapshot`, `embedder`, `search`, `olis-client` and `database` build on those (`legislators` and `agency-links` on `domain` alone, `recording-log` on nothing (its input types are its own), `statute-links` on `domain` and `time`'s `Timestamp` type, `pdf-text` on neither), and `ingest` and `mcp-server` sit on top. `src/bin/ingest.ts` and `src/bin/server.ts` are the two entry scripts: each loads its configuration and creates what it needs (the clock, `fetch`, the shutdown signal, and for the server its pino logger) once, and passes it down.

**What the OLIS client reads so far.** Ticket #4 reads one entity set, Measures. Of the feed's quirks (`src/CLAUDE.md`, "Shape"; `docs/research/olis-odata.md` sections 1 and 8) the client therefore handles, and the tests show, `$inlinecount`, paging with a relative `odata.nextLink`, `/$count` without a JSON `Accept` header, and timestamps with no offset. Decimal keys serialized as strings and misspelled property names do not occur in Measures: they are in sets the client does not read yet (`MeasureSponsors`: `MeasureSponsorId` and `LegislatoreCode`; `MeasureAnalysisDocuments`: `MeasureAnalysisId` and `CommittteCode`; `CommitteeAgendaItems`: `CommitteCode`). The first ticket that reads one of them handles the quirk in `olis-client/lib/`, exposes the corrected name or number as a domain type, and shows it through a tool. Reading a set only to exercise a quirk, with nothing an agent could see, would have meant a test below the tools, which `test/CLAUDE.md` does not agree as a seam.

**Ticket #8 reads two more sets.** The client now reads `Legislators` and `MeasureSponsors`, and handles the quirks the paragraph above says were waiting for them: `LegislatoreCode` is read under its misspelled name and handed on as `legislatorCode`, and `MeasureSponsorId` and `PrintOrder` arrive as strings and leave as numbers. `get_measure` shows the sponsors through the tool, which is where the test sees the quirks. The sponsors are stored in `legislator` and `sponsor` tables in the same transaction as the Measures, resolved by the worker, so the server needs neither the alias file nor the resolver. The `sponsor` table keeps every MeasureSponsors row with its kind, so the Committee and Presession rows, which name no Legislator, are not lost: `get_measure` shows them as `committee_sponsors` and `presession_messages`. The reader puts the Member rows in print order with `comparePrintOrder` (`domain/legislators.ts`), since that order depends on the Measure's own chamber and on names, which no column of the feed holds. The alias file is `legislators/data/legislator-aliases.json`; `src/bin/ingest.ts` passes its path (`committedAliasFilePath`, exported by `aliases.ts`) to `readLegislatorAliases`, so a seam-1 test gives the worker another file through `startSystem`.

**Ticket #15 reads four more things.** The client now reads the location fields of Measures (`CurrentLocation`, `CurrentCommitteeCode`) and three more sets, `MeasureHistoryActions`, `MeasureVotes` and `CommitteeVotes`, and `get_measure` shows them as `location`, `history`, `floor_votes` and `committee_votes`, as of the last full pull; the live status block is ticket #21's. None of the quirks that paragraph above kept for later is in them: no decimal key is sent as a string and no property is misspelled (`docs/research/olis-votes.md` §1 has the cache's types for every property of the four). What they do have, and what the client handles and the tests show through the tool:
- Timestamps with no offset: `ActionDate` (history and floor votes) and `MeetingDate` (committee votes) are read as Pacific local time through the same `feedTimestamp` as `CreatedDate`, and refused with an offset. `get_measure` shows each with the offset in force that day.
- Property names that say something else: the Legislator Code of a vote is in `VoteName`, and the vote itself is in `Vote` in `MeasureVotes` but in `Meaning` in `CommitteeVotes`. The client hands on `legislatorCode` and `vote` for both.
- The chamber is a letter ("H", "S"); the client hands on `house` or `senate` and refuses any other letter.
- One row for each Legislator in each vote: the client hands on one entry for each row, and the reader groups them, a floor vote by `MeasureHistoryId` and a committee vote by `CommitteeReportId`. The feed gives some committee rolls twice, as two reports of the same rows (`docs/research/olis-votes.md` §3), so the reader lists a roll once when a later report of the same committee and meeting holds the same Legislator Codes with the same votes. It keeps two rolls that differ as two votes, so no row of the feed is dropped.

The worker resolves the Legislator Code of every vote entry through the resolver, counted against the sources `MeasureVotes` and `CommitteeVotes` in the build report, and stores the entry with the Legislator's id in `floor_vote` and `committee_vote`, in the same transaction as everything else. The `history_action` table and the two columns that the `measure` table gained (`location`, `committee_code`) are written there too. The vote word is kept as the feed's string, since nothing branches on it and a closed set would stop a pull on the first new word. Committee codes are shown as codes: committee names wait for the ticket that reads `Committees`. The tables were created with `CREATE TABLE IF NOT EXISTS`, so a database file built by an earlier version has no `location` column on `measure` and the worker's pull fails with SQLite's "table measure has no column named location" (`docs/research/olis-votes.md` §7); no database has been deployed (tickets #24 and #25), so the answer is to rebuild it, and a migration waits for the first release that needs one.

**Ticket #21 adds an entry point and a client method for the live lookup.** What `get_measure` reads from OLIS when it is called, what a failed read is, and what the server needs in order to read it are ADR-0014's decision; this ADR records only where the code sits.
- `domain/schedule.ts` is a new entry point of `domain`: `AgendaItem` and its order.
- The OLIS client gains one method on its existing entry point, `readMeasureLive(key, readAt, signal)`, so the only code that sees the feed's shapes is still the code that reads them, live or in a pull. The feed's misspelled `CommitteCode` is read in `olis-client/lib/agenda-items.ts` and handed on as `committeeCode`.
- `mcp-server/lib/live-status.ts` calls it and decides what a failure is. It groups the vote entries with the same functions the reader uses: `groupFloorVotes` and `groupCommitteeVotes` (with the repeated-roll rule) moved to `domain/votes.ts` for that.
- The worker writes a `legislator_code` table (code to Legislator id) beside the other tables, from the resolver, because the server has neither the alias file nor the resolver.
- `src/bin/server.ts` creates and passes down what the lookup needs, as `src/bin/ingest.ts` does for the worker: `fetch`, the shutdown signal, the OLIS base URL and the bound on a lookup, with a callback that logs a lookup that failed.

**Extended by ticket #9, search (ADR-0025, ADR-0026).**
- Two packages are added. `embedder` is the interface the worker and the server are given (`index.ts`), its real implementation (`onnx.ts`, onnxruntime-node and `@huggingface/tokenizers`) and the lock of the pinned model (`lock.ts`). `search` is pure: `passages.ts`, `documents.ts`, `text.ts`, `vectors.ts` and `ranking.ts` import `domain` and `node:crypto` and nothing else, so the worker and the server share them.
- `domain` gains two entry points. `search.ts` holds the types of what the index keeps (`SearchEntry`, `Passage`); `citations.ts` reads Measure, Proposed Amendment and ORS citations out of a question as the ids they stand for, with the functions that already mint those ids. `DocumentLink` gains `date`, which the OLIS client sets (the meeting's start for anything posted to or for a meeting, else the row's `CreatedDate`).
- `database` gains an entry point, `search.ts`, the server's read-only queries of the search index (keyword matches, cited documents, hit details, the vectors to hold in memory), and the tables `search_document`, `passage`, `passage_fts` (FTS5, contentless), `document_citation` and `passage_vector`. `writer.ts`'s `storeDocument` takes the document's search record and writes it in the same transaction; `refreshDocuments` updates the search entry with the rest of the row.
- `ingest` takes an `Embedder`: it counts tokens to cut passages and embeds the passages the index does not hold, and `build-report.json` counts them. `config` requires `MODEL_PATH` for the worker and the server and reads `MODEL_THREADS` (default 1) for the worker. `src/bin/ingest.ts` and `src/bin/server.ts` load the model from `MODEL_PATH` with the committed lock file's path and pass the embedder down.
- `mcp-server` registers `search` (`lib/search.ts`) and holds the vectors in memory (`lib/vector-cache.ts`).
- The tests' fake embedder (the real tokenizer over a fake `ModelRunner`) and the loader of the real one are in `test/support/`.

**Extended by ticket #10, the OregonAI snapshot (ADR-0012).**

**Extended by ticket #125, the Recording Log parser (spec #123).** One package is added; no entry point of another package changes.
- `recording-log` (`index.ts`) is test seam 2: `parseRecordingLog` takes the log's text, the PDF's link annotations (`RecordingLogLink`, as pdf.js gives them, with the page number) and, optionally, the Meeting's Agenda items as the feed gives them (`FeedAgendaItem`, from `CommitteeAgendaItems`). It reads no PDF and no feed itself: `pdf-text` and `olis-client` stay the only code that do, and a later ticket wires the three together in `ingest`.
- An Agenda item is a log line that matches one of the feed's items (the measure id and its action, or the item's text), reported with `foundBy: "feed"`. Otherwise the text heuristic decides that line, reported with `foundBy: "text"`, except that a line shaped like a person ("Name, Title", or "Name - Organization" where the right side reads like an organisation or "Self") is never taken by it. Each line is decided on its own: the first version of this rule (owner decision Q5, 2026-11-05) used the text heuristic only when no feed item matched any line of the log, and the owner amended it the same day (ticket #126, decision A, ADR-0052) because a feed that holds some of a Meeting's items left the others' lines as speakers.
- A page whose links cannot be matched to its timecode lines is read from its timecodes, and the result lists such pages (`pagesReadByTimecode`) for the build report (Q6). Vote names are dropped in stage 1 (Q7).

**Extended by ticket #95, the Index's schema version (ADR-0048).** No package is added; `database` gains one entry point, `checkpoint.ts`.

**Extended by ticket #98, the tool result envelope.** No package is added; `mcp-server` gains one entry point, `envelope.ts`.

It holds everything a result carries that is not a tool's own: the rate limit (moved from the tool contract, so no tool calls it and none can skip it), the As of, read once for each call and handed to the tool, the notice, the Staleness warning (ADR-0039) as one more block of text after the tool's own, and the MCP result (the content pair, `isError`). An Index with no As of, which is every Index before its first complete Full pull, answers every tool with one error, after the rate limit counts the call. The envelope adds `as_of` and `notice` to each tool's output schema, so a tool's schema holds its own fields only and stays the single source of its `outputSchema`.

- Each file of `lib/` that is a tool exports its schemas, its function (which returns an `Outcome`, and is given the As of) and its fault message; `handler.ts` registers it with the envelope and keeps no rule of the result. A new tool is registered the same way.

**Extended by ticket #96, the Snapshot read (ADR-0027, ADR-0035, ADR-0044, ADR-0047).** No package is added; `ingest` gains one entry point, `snapshot-read.ts`, named after the glossary's Snapshot.
- `beginFullPullSnapshotRead({ writer, session, snapshot })` and `beginIncrementSnapshotRead({ writer, session, snapshot })` begin a Pull's Snapshot read, one for each kind of Pull so that the types say what `finish` takes and gives. A Full pull reads, and switches the Index to its Snapshot. An Increment decides once, when it begins, whether it reads: it does when the Snapshot file is the one the Index reports, and otherwise it reads nothing and leaves it to the next Full pull. `database` stays storage and imports no parser; this module calls the parsers (`statute-links`, `agency-links`, `pdf-text`) and the writer.
- The Pull stores the Testimony rows through `testimonyRecordsOf(links)`, at the moment it stores them, so that a server reading during a Pull never sees a stored row lose its Agency: matched with the Snapshot's registry when the Pull reads, left alone when it does not (ADR-0047). `ingest/index.ts` no longer matches Testimony or decides what an Increment may read.
- `finish` is called once the Pull's documents are stored (a second call throws). It reads the Statute Links of the stored Versions and postings not yet read with the Snapshot, then their Agency Links (ADR-0035), then the series of the Statutes Affected Table (ADR-0044), and records the Snapshot last, so a run that stops earlier leaves the Snapshot of the last run that finished and the next run reads what is still unread. Before this ticket the Snapshot was recorded before the table was read again, so a run that stopped at the table reported a Snapshot the table's series were not read with.
- Fetching the Statutes Affected Table from its address stays with the Pull, which hands a Full pull's `finish(table)` what it got (the bytes, or why there are none) or nothing when the deployment names none; `lib/statutes-affected-table.ts` reads that instead of fetching it, and the build report's block is as it was. The Full pull's `finish` always returns the read with the table's report or its absence. An Increment's `finish()` takes no table, so handing it one does not compile, and returns `read` or `left_to_full_pull`.
- The four tables that stamp what was read with which commit (`statute_read`, `agency_read`, `statutes_affected_read`, `snapshot_state`) are as they were, and the writer's methods for them are called by this module alone. `.dependency-cruiser.cjs`'s `worker-writes-only` skips `ingest/tests/`, so the module's seam-4 tests (`ingest/tests/snapshot-read.test.ts`) read back through `database/reader.ts`.

**Extended by ticket #99, the Statute Links of a Measure (ADR-0015, ADR-0033, ADR-0036).** No package is added; `statute-links` gains two entry points, `measure.ts` for one Measure and `table.ts` for the whole table.

Its seam-4 tests are in the package's `tests/`: they call it with no database, and every case names a real Measure.

It was `domain`'s `versionDescriptionOfEntry`, which `get_measure` called, beside a second reading of the same rule in the Build report (`entry.loneE` and the writer's `measuresListingVersion`); the function, under the same name, is now in the package's `lib/`, behind the entry points. **Extended by ticket #100, the Pull register (ADR-0050).** No package and no entry point is added; two existing entry points change, and `ingest` and the Listing change inside.
- `ingest` holds the register in `lib/pull-register.ts`, which is not an entry point: nothing outside `ingest` reads it. `readFeed` in `index.ts` asks it how to read each set, and `createWorkerClient` makes the one OLIS client every run of the worker uses; `ingest`'s entry points are as they were.
- `olis-client/index.ts`: every `readX(session, signal)` of a Pull becomes `readX(session, read, signal)` with a `PullRead` (`whole`, `changed_since` or `above_id`), `readFloorLetters` loses its `aboveId` parameter for the same `read`, and `readDocumentLinks` returns the links of its five sets apart (`DocumentSets`). The `changedSince` option of `createOlisClient` is gone. The live lookup's `readMeasureLive` is as it was.
- `database/writer.ts`: `IndexWriter` gains `asOf(session)`, the same answer as the reader's, written once in `lib/run-state.ts`. `FullPullRecord` has one field for each name in `pulledEntitySets` (its types move to `lib/pull-record.ts` and `writer.ts` still exports them).
- `documentLinksOf(record)` is exported from `writer.ts` beside the record. It joins the documents a record holds in the order the worker fetches them (ADR-0011), which is the worker's rule and sits in `database` all the same: the writer stores from the same list, so the one function is called by the writer and by `ingest`, and the list is written once.
- `database/lib/listing.ts` keys the rows of each entity set in one table, in place of `ListedSources`, `listedRowsOf`'s loop over fields and `entitySetOfDocument`.

**The database is two entry points, not one.** The worker writes and the server reads (ADR-0007), and the SQLite connection modes differ: `writer.ts` opens with WAL and `timeout: 5000`, `reader.ts` opens `readOnly` with `timeout: 5000`. Giving each side its own entry point lets the boundary check say that the server's code and entry script may import `reader.ts` and never `writer.ts`, and that the worker may import `writer.ts` and never `reader.ts` (the `server-reads-only` and `worker-writes-only` rules in `.dependency-cruiser.cjs`). A server that cannot reach the writer cannot write by mistake. Later tickets add queries to `reader.ts` and `writer.ts` (or further entry points beside them, such as a search index) rather than a second way into SQLite.

**Time and ids are packages of their own.** The worker dates a pull and the client dates every row, and what the server shows has to agree with both; the configuration, the client, the database and the server all use the same ids. So each lives once, in a package at the bottom. Pacific time uses Node 26's native `Temporal`, not the process time zone, which is why the tests run under a zone other than Pacific. How the feed writes a timestamp (no offset, read as Pacific) is a feed shape, so `src/CLAUDE.md` keeps it in the OLIS client: `time` turns a Pacific wall-clock reading into a `Timestamp` and the client's `lib/timestamps.ts` is the only code that reads the feed's text. (A time a person writes in a tool argument is ISO 8601, not a feed shape, and `time` reads it, so that no tool spells the zone: `readTimestamp`, ticket #16.)

Later tickets add packages as their modules arrive (the document store, the Statute Link parser, the Agency Link extractor, the embedder, search) and add entry points to these. A new MCP tool is a file in `mcp-server/lib/` registered in `handler.ts` through the envelope (ticket #98), which the file leaves the rate limit, the As of, the notice and the result to.

## Considered Options

- **One package per spec module, all twelve now.** Most would be empty folders, and their interfaces would be guesses before any caller exists.
- **One `core` package.** Nothing would be hidden, and the read-only server could reach the writer.
- **Separate packages for the writer and the reader.** They share one schema and one connection module, so splitting them would duplicate the schema or expose it.
- **A types-only package beside `domain`.** Minting an id needs the types it returns, so the two stay together.
