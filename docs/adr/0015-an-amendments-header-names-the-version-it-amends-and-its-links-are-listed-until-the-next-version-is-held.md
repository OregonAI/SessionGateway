# An amendment's header names the Version it amends, and its Statute Links are listed until the next Version is held

ADR-0001 says a Proposed Amendment is parsed only for what it says itself, and that "when the next Version is printed, its parse replaces these links for that Measure". Ticket #13 builds `compare_amendment` and the Statute Links of `get_measure` on that, and this ADR records the four things the ticket left to the code (2026-10-30, corrected after review the same day).

**The links are read from stored text, once for each distinct file.** After a full pull has stored its files, the worker reads every stored Version and every posting of a Proposed Amendment that has not been read, from the text the store holds (`statute_parse` and `statute_link`, keyed by the file's content hash and what it was read as), with `parseStatuteLinks` and the snapshot's ORS section list. The stored text is PDF.js's (ADR-0010), whose page furniture differs from `pdftotext`'s: the parser's footer rule takes both footers, and the seam-2 tables quote both. Nothing is fetched again, so a parser that improves can read the stored files again without a download, and two postings that share a file share one reading. A Printed Amendment, an analysis document, an Exhibit and every other kind of document is not read: the ticket names Versions and Proposed Amendments. A file with no text layer is recorded as not read and has no links; `get_measure` and `compare_amendment` say so (`text_read` and `not_read_reason`) instead of showing an empty list, and the build report already lists the file among the documents with no text layer (ADR-0011). Postings whose files differ in bytes but whose text was read and reads the same (SB 69-1's postings 26284, 26285 and 26287 are three postings and two files: 26285 and 26287 are byte-identical, and 26284 differs in the PDF's modification date) are one entry with every posting id. Files that read differently are separate entries, each with its posting ids, and none is picked. Two different files that were both not read have said nothing about what they hold, so they are separate entries too; only postings that share one file are one entry.

**The Version an amendment amends is read from its header and checked against its number.** The first page says "PROPOSED AMENDMENTS TO", then "SENATE BILL 69" for an amendment to the Introduced Version of SB 69 or "A-ENGROSSED HOUSE BILL 3795" for one to the A-Engrossed Version of HB 3795. The header names a Measure as well as a Version, and the Measure must be the amendment's own: a file posted under the wrong Measure gives "not known", with a reason that names both. The amendment's number says the Version too: a number alone ("-2") for Introduced, a letter and a number ("-A3") for that engrossed Version. The feed spells one amendment's number more than one way ("-1", "1" and "- 1" are one amendment, because its id is minted from the number), so the number is parsed in one place, in the domain, with the id: a number with an optional Version letter, with or without the hyphen, and the Version is read from the number of every posting, not the earliest alone. `compare_amendment` names the Version only when the header, the number and the Measure agree and the store holds that Version. Otherwise it says the Version is not known and why (no file held, an unreadable header, a header that names another Measure, headers that name different Versions, a number that names none, postings that spell the number so that it names different Versions, a disagreement, a Version not held), and still lists the amendment's own links with no comparison. This is ADR-0013's rule, applied to amendments: nothing is guessed, because a director briefed on the wrong Version is told the wrong change. The worker reads the header (a pure function of the text, `readAmendedVersionHeader`) and keeps the Version and the Measure it names; the server compares them with the number and the Versions the store holds.

**"Replaces" is a state, not a date.** `get_measure` lists a Proposed Amendment's links while the store holds no Version later than the one it amends, and leaves them out once it does; the later Version's own links are listed in their place. The Version an amendment amends is the one its header and number name, whether or not the store holds that Version's file: a Version whose download failed still sits in the order, so an amendment to A-Engrossed is replaced when B-Engrossed is held. Versions are ordered Introduced, A-Engrossed, B-Engrossed and so on by letter, then Enrolled; a description that sits nowhere in that chain ("Minority Report A-Engrossed") is neither later than any Version nor replaces any amendment. An amendment whose Version cannot be named stays listed, labelled so. The left-out amendments are listed apart (`superseded_amendments`, with the Version each amends, which is not held when its file did not come, and the Version that replaces it), and `compare_amendment` still answers for them. The rule follows what the store holds, so a pull that brings the next Version in changes the answer with no other event.

**A document's links are shown by kind, each target once with the measure sections it is linked in.** `get_measure` and `compare_amendment` write a document's Statute Links as `amends`, `repeals`, `adds-to` and `cites`, each with its ORS sections and its ORS chapters apart; every target is one entry with the list of measure sections it is linked in, and a chapter keeps `resolvable_on_oregonai: false` on its own entry. Nothing is left out. This is the form that keeps the answer short enough to read: a range such as ORS 659A.150 to 659A.186 is one citation for each section in it, and SB 69's A-Engrossed and Enrolled Versions have 292 links each.

## Considered Options

- **A date rule**: replace an amendment's links once the next Version is dated after the amendment. The feed dates a Version's file row, not its printing, and a Version can be posted before or after the meeting that adopted the amendment; a state rule needs no date and cannot disagree with the Versions the tool shows.
- **Trust the number alone when the header cannot be read, or when it names another Measure.** Fewer "not known" answers, but a mis-numbered or mis-posted file would be compared against the wrong Version without a word.
- **Read the number from the earliest posting, as the feed spells it.** The Version then depends on posting order and spelling (HB 2344's first posting of -1 reads "1"), and the id is minted from the number by a different rule.
- **Replace an amendment only when the Version it amends is itself held.** A failed download then keeps a replaced amendment's links listed as current beside the later Versions.
- **Read each posting, not each file.** Simpler tables, but every posting would be parsed again for bytes the store already read, and nothing would say that two postings of one amendment read the same.
- **Read the files as they are fetched.** One step fewer, but a parser fix would need every file fetched again, which ADR-0005 does not allow us to do casually.
- **List every amendment's links in `get_measure`, replaced or not.** Nothing to explain, but a Measure whose A-Engrossed Version adopted -1 and -2 would show the same links three times, and an agent could read a replaced amendment's links as the Measure's current text.
- **One flat object for each link and measure section** (kind, target, type, resolvable, section). Each link is self-contained, but SB 69's `get_measure` answer grew from 33,229 characters on `main` to 104,623, most of it the 292 links of each of two Versions repeated at about 120 characters each. Rejected after review for the form above, which keeps every link.

## Consequences

- A Measure with large ranges still makes a large answer: SB 69's `get_measure` is 65,272 characters (33,229 on `main`), 32,016 of them the Statute Links of its Versions, because each of the A-Engrossed and Enrolled Versions cites 261 targets in 283 links. Whether `get_measure` should give cites as counts per source, which would make the answer 36,700 characters, is the owner's question on the PR; a filter by kind is the other follow-up.
- The links are read once for a file. A new snapshot changes how ranges expand (the section list), and a worker that finds a file already read does not read it again; a deployment that changes its snapshot rebuilds the database, as ADRs 0012 and 0014 already say for schema changes. A parser fix is the same: delete the file's reading, and the next pull reads it again from the stored text.
- A pull that stops between storing a file and reading it leaves the file unread until the next pull. The tools show it as not read, with the same words as a file with no text layer.
- A later Version replaces an amendment even when its own text was not read (a scan). `get_measure` shows that Version with `text_read: false`, and `compare_amendment` still answers for the amendment.
- The stored text is PDF.js's, not `pdftotext`'s, so the parser is tested on both. The fixture holds 33 Versions and postings that are read (18 Versions and 15 postings; its 5 Printed Amendments are not read). Before the footer rule took PDF.js's footer, which is two lines where `pdftotext`'s is three ("Proposed Amendments to SB 69 Page 13"), the links read from the stored text differed from those read from `pdftotext` for SB 69-1's three postings (the citation "ORS" / "659A.270" across a page break was lost), and for 5 of 75 sampled amendments of the research cache; after it they agree for all 33 and all 75. A header that PDF.js writes differently from `pdftotext` is the same kind of risk, and the table of headers (`amended-version.test.ts`) has rows in both forms.
