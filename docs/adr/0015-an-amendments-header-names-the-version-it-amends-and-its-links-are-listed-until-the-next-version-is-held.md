# An amendment's header names the Version it amends, and its Statute Links are listed until the next Version is held

ADR-0001 says a Proposed Amendment is parsed only for what it says itself, and that "when the next Version is printed, its parse replaces these links for that Measure". Ticket #13 builds `compare_amendment` and the Statute Links of `get_measure` on that, and this ADR records the four things the ticket left to the code (2026-10-30).

**The links are read from stored text, once for each distinct file.** After a full pull has stored its files, the worker reads every stored Version and every posting of a Proposed Amendment that has not been read, from the text the store holds (`statute_parse` and `statute_link`, keyed by the file's content hash and what it was read as), with `parseStatuteLinks` and the snapshot's ORS section list. Nothing is fetched again, so a parser that improves can read the stored files again without a download, and two postings that share a file share one reading. A Printed Amendment, an analysis document, an Exhibit and every other kind of document is not read: the ticket names Versions and Proposed Amendments. A file with no text layer is recorded as not read and has no links; `get_measure` and `compare_amendment` say so (`text_read` and `not_read_reason`) instead of showing an empty list, and the build report already lists the file among the documents with no text layer (ADR-0011). Postings whose files differ in bytes and read the same (SB 69-1's three, which differ in the PDF's modification date) are one entry with every posting id; files that read differently are separate entries, each with its posting ids, and none is picked.

**The Version an amendment amends is read from its header and checked against its number.** The first page says "PROPOSED AMENDMENTS TO", then "SENATE BILL 69" for an amendment to the Introduced Version or "A-ENGROSSED HOUSE BILL 3795" for one to an engrossed Version, and the amendment's number says the same: digits alone ("-2") for Introduced, a letter and digits ("-A3") for that engrossed Version. `compare_amendment` names the Version only when the header and the number agree and the store holds that Version. Otherwise it says the Version is not known and why (no file held, an unreadable header, a number that names none, a disagreement, a Version not held), and still lists the amendment's own links with no comparison. This is ADR-0013's rule, applied to amendments: nothing is guessed, because a director briefed on the wrong Version is told the wrong change. The worker reads the header (a pure function of the text, `readAmendedVersionHeader`) and keeps what it names; the server compares it with the number and the Versions the store holds.

**"Replaces" is a state, not a date.** `get_measure` lists a Proposed Amendment's links while the store holds no Version later than the one it amends, and leaves them out once it does; the later Version's own links are listed in their place. Versions are ordered Introduced, A-Engrossed, B-Engrossed and so on by letter, then Enrolled; a description that sits nowhere in that chain ("Minority Report A-Engrossed") is neither later than any Version nor replaces any amendment. An amendment whose Version is not known stays listed, labelled so. The left-out amendments are listed apart (`superseded_amendments`, with the Version that replaces each), and `compare_amendment` still answers for them. The rule follows what the store holds, so a pull that brings the next Version in changes the answer with no other event.

## Considered Options

- **A date rule**: replace an amendment's links once the next Version is dated after the amendment. The feed dates a Version's file row, not its printing, and a Version can be posted before or after the meeting that adopted the amendment; a state rule needs no date and cannot disagree with the Versions the tool shows.
- **Trust the number alone when the header cannot be read.** Fewer "not known" answers, but a mis-numbered or mis-posted file would be compared against the wrong Version without a word.
- **Read each posting, not each file.** Simpler tables, but every posting would be parsed again for bytes the store already read, and nothing would say that two postings of one amendment read the same.
- **Read the files as they are fetched.** One step fewer, but a parser fix would need every file fetched again, which ADR-0005 does not allow us to do casually.
- **List every amendment's links in `get_measure`, replaced or not.** Nothing to explain, but a Measure whose A-Engrossed Version adopted -1 and -2 would show the same links three times, and an agent could read a replaced amendment's links as the Measure's current text.
- **Group a file's links by kind and section.** A smaller payload, and a nested shape that every consumer must flatten; each link carries its kind and section instead.

## Consequences

- A Measure with large ranges makes a large answer: SB 69's Enrolled Version has 292 Statute Links, most of them citations from the ranges in SECTION 6. `get_measure` lists every link of every Version. A filter by kind is the follow-up if agents find the answer too long.
- The links are read once for a file. A new snapshot changes how ranges expand (the section list), and a worker that finds a file already read does not read it again; a deployment that changes its snapshot rebuilds the database, as ADRs 0012 and 0014 already say for schema changes. A parser fix is the same: delete the file's reading, and the next pull reads it again from the stored text.
- A pull that stops between storing a file and reading it leaves the file unread until the next pull. The tools show it as not read, with the same words as a file with no text layer.
- A later Version replaces an amendment even when its own text was not read (a scan). `get_measure` shows that Version with `text_read: false`, and `compare_amendment` still answers for the amendment.
- A header that PDF.js writes differently from `pdftotext` is a risk the table of headers (`amended-version.test.ts`) and the seam-1 cases share: the stored text is PDF.js's (ADR-0010). On the fixture's thirty-eight Versions and Proposed Amendments the two readers give the same Statute Links except for one citation that crosses a page break in SB 69-1, where the footer's last two lines are one line in PDF.js's text ("Proposed Amendments to SB 69 Page 13"), which the parser's footer rule does not match, so the citation "ORS" / "659A.270" is not joined across the break. That is ticket #6's parser, and it is reported on the ticket's PR, not changed here.
